## 2. 작업 방식

### 2.1 기능 하나의 흐름
1. **코드 조사**: 바꿀 기능이 닿는 곳을 `grep`으로 모두 찾습니다(호출부, 테스트, 예제, i18n).
2. **계획 v1 작성**: 문제, 설계 결정, 파일 형식, GUI, 테스트, 열린 질문을 씁니다.
3. **교차 모델 리뷰**: Gemini Argon(`gemini-4-argon-high`)에게 저장소 읽기 권한을 주고 계획을 리뷰받습니다. 2.2를 보세요.
4. **리뷰 검증**: Argon이 근거로 든 `파일:줄`을 직접 열어 확인합니다. 틀린 지적은 버립니다(5.2).
5. **계획 v2 작성 후 구현**: 엔진(Qt 없음) 커밋과 GUI 커밋을 나눕니다.
6. **검증**:
   - `QT_QPA_PLATFORM=offscreen python -m pytest`
   - 해석해 비교 테스트
   - 영문·한글 화면을 오프스크린으로 캡처해 눈으로 확인합니다. 테스트가 못 잡는 레이아웃 문제를 매번 여기서 찾았습니다(5.3).
6a. **(선택) 모의 실행·블라인드 테스트**: 사용자가 따라 할 절차가 있는 기능은, 구현 전에 엔진을 직접 돌려 절차를 끝까지 따라가 보고, 문서만 읽은 다른 에이전트에게 같은 과제를 시켜 짐작한 지점을 찾습니다(3.12). 리뷰가 놓친 문제를 여기서 찾았습니다.
7. **PR**: 설명에 이유, 호환성, 검증, 미룬 것을 적습니다. 로컬에서 Python 3.10과 3.13 두 환경의 테스트가 모두 통과하면 머지합니다(2.3). PR #10까지는 CI 12개(3 OS × Python 3.10/3.13 × push/PR) 통과가 조건이었습니다.

### 2.2 agy(Antigravity) 리뷰 요령
- **읽기 전용 권한은 세션 설정으로 줍니다.** 전역 설정은 건드리지 않습니다.
  ```json
  {"permissions": {"allow": ["command(grep)", "command(rg)", "command(ls)", "command(cat)", "command(sed)",
    "command(head)", "command(tail)", "command(find)", "command(wc)", "command(git log)",
    "command(git show)", "command(git diff)"]}}
  ```
  호출 예: `agy --model gemini-4-argon-high --mode plan --settings <위 JSON 파일> --add-dir <저장소> --add-dir <리뷰 자료> -p="<프롬프트>"`
- **실패와 원인**: 비대화식(headless) 모드에서는 거부가 한 번만 나도 턴이 답 없이 끝납니다.
  - 처음 두 번은 셸 명령 거부로 실패했습니다. 두 번째에는 `find`가 허용돼 있었는데도 실패했습니다. 명령에 와일드카드(`README*`)가 들어가 "unknown_command"로 분류됐기 때문입니다.
  - 해결책: 프롬프트 첫머리에 "허용 명령 목록, 와일드카드·파이프 금지, 거부되면 턴이 끝남"을 적습니다.
- **실패 원인 묻기**: 실패한 대화를 `--conversation <ID>`로 이어서 "왜 그 명령을 쓰려 했는가"를 물으면 정확한 답을 받습니다. 대화 ID는 `~/.gemini/antigravity-cli/log/cli-*.log`의 "Created conversation" 줄에 있습니다.
- **모든 도구 자동 승인은 막힘**: `--dangerously-skip-permissions`는 Claude Code 권한 검사에서 막혔습니다. 우회하지 말고 위의 읽기 전용 방식을 씁니다.
- **3.19 리뷰 실행 기록** (agy 1.5.2, 2026-11-08):
  - 위 프롬프트 첫머리 제약을 넣자 한 번에 끝까지 돌았습니다(거부 없음). Bash 툴 2분 제한을 피하려고 백그라운드로 실행했습니다.
  - 답에는 `file://` 링크가 붙어 31 KB였습니다. 링크 대상을 지우면 17 KB로 줄어 읽기 쉽습니다(`sed -E 's#\]\(file://[^)]*\)#]#g'`).
  - 프롬프트에 "모든 지적에 `파일:줄`, 코드에서 확인 못 한 것은 '추측'으로 표시, 칭찬·요약 없이 중요도 순 최대 15개"를 요구했습니다.
    지적 15개 중 14개가 코드로 확인됐고, 기존 버그 4개를 찾았습니다. '추측'으로 표시된 1개는 측정으로 판정했습니다(5.2).
- **3.24 리뷰 실행 기록**: 같은 두 문장에 "인용하기 전에 그 줄을 읽어라", "질문을 바꾸거나 빼지 마라"를 더하고 저장소 밖 동작은 '지식 기반'으로
  표시하게 했더니, 열린 질문 4개에 모두 번호대로 답했고 코드 인용도 맞았습니다. 지식 기반 주장(Qt의 avoid 미지원, 다크 팔레트 영향 등)은 시제품과
  실험으로 하나씩 확인했습니다.
- **3.23 리뷰 실행 기록**: 3.22와 같은 두 문장을 넣었지만 이번에는 덜 지켰습니다. 지적 8개의 요지는 모두 코드와 맞았으나 세부 두 개를 지어냈고
  (`test_optimize_tolerance.py:398`의 `angle_mode == "target_grid"`, 없는 함수 `spectral.apply_axis`), 열린 질문 4개 중 2개(스키마를 올릴지, 맵이 따를지)는
  답하지 않고 묻지 않은 질문 2개에 답했습니다. 같은 프롬프트로도 결과가 달라지므로, 리뷰의 인용과 질문 답은 매번 대조합니다(답하지 않은 질문은 직접 판단하고 그렇게 적음).
- **3.22 리뷰 실행 기록**: 프롬프트에 (1) 지난 리뷰의 틀린 주장을 알려 주고 "모든 사실 주장은 파일:줄을 읽고 확인한 뒤에만, 못 하면 '추측'",
  (2) "열린 질문에 번호 그대로 답하고 질문을 바꾸거나 새로 만들지 말라"를 넣었더니, 지적 9개가 모두 코드와 맞았고 질문 4개에 번호대로 답했습니다.
  남은 작은 오류는 지적 9의 `SCHEMA_VERSION = 3`(실제 6) 하나였습니다. 앞으로도 이 두 문장을 넣습니다.
- **3.21 리뷰 실행 기록**: 메타문자 금지 제약을 넣은 첫 시도로 끝났습니다. 다만 이번에도 "열린 질문" 절은 계획의 질문 4개 중 2개만 답하고 나머지는
  스스로 바꾼 질문(두께 단위, 앱 기본 단위)에 답했습니다. 질문 번호 그대로 답하라고 적어도 생기므로, 답을 계획의 질문과 대조해 씁니다.
- **3.20 리뷰 실행 기록**: 같은 방식으로 한 번에 끝났습니다. 계획 파일 끝에 "정해야 할 것"을 넣고 "각각 의견과 근거"를 요구하자, 근거 있는 의견(기존 테스트와의 충돌 등)을 받았습니다. 지적 14개 모두 코드로 확인됐고 기존 버그 2개를 찾았습니다.
- **2.4절 리뷰에서 나온 실패 두 가지** (2026-11-08):
  - 괄호도 거부됩니다. `grep -rn open( src …`가 셸 메타문자로 분류돼 턴이 답 없이 끝났습니다. 로그의
    `soft-denying tool confirmation "RunCommand"` 줄로 실패를 알 수 있고, 같은 대화를 `--conversation`으로 이어 "도구 없이 텍스트로,
    거부된 명령의 정확한 문자열"을 물으면 원인을 답합니다. 이후 프롬프트 제약에 "명령 인자에 괄호·대괄호·중괄호·`$`·따옴표·백슬래시·
    세미콜론 금지, 검색 패턴은 영문자·숫자·밑줄·점·하이픈·슬래시만"을 넣었고, 그 뒤로는 실패하지 않았습니다.
  - 실패한 대화를 이어서 리뷰를 끝내게 했더니, 지적은 정확했지만 "정해야 할 것"에는 계획에 없는 질문 네 개를 지어내 답했습니다.
    재개한 답은 계획의 질문 목록과 대조해 걸러 씁니다.
- **UI 리뷰 자료**: Argon은 앱을 띄울 수 없습니다. 오프스크린 캡처 이미지를 함께 줍니다.
  - 캡처할 때 `gui/app.py`의 시작 루틴(Qt 번역기 로드)을 거치지 않으면 표준 버튼이 영어로 찍힙니다.
  - 이것을 번역 누락으로 오인한 사례가 있었습니다(5.2).

### 2.3 CI 운용
- **2026-11-07부터 CI는 수동 실행만 합니다.** 저장소가 비공개라 Actions 사용 시간이 과금 대상입니다(macOS 10배, Windows 2배로 계산). push와 PR마다 12개 작업을 자동으로 돌리다가 사용 한도에 도달했고, PR #11의 CI는 "결제 실패 또는 사용 한도" 메시지와 함께 시작되지 못했습니다. 사용자가 비용을 낼 수 없다고 해서 자동 실행을 껐습니다.
- **머지 전 검증**: 로컬 conda 환경 `coat-py310`, `coat-py313`에서 `QT_QPA_PLATFORM=offscreen python -m pytest`를 돌립니다. 이 방법은 macOS만 확인합니다. Windows·Linux 고유의 문제(경로, 신호 처리, 글꼴)는 사용자가 CI를 직접 실행할 때만 드러납니다.
- **로컬 환경 함정**: 이 맥(macOS 27)에서는 Python 3.10용 pip SciPy 휠(1.15.3)을 로더가 거부합니다(`__thread_bss` zero-fill 섹션 오류). 그래서 SciPy를 쓰는 테스트 모듈 5개가 수집 단계에서 실패했습니다. conda-forge 빌드(1.15.2)로 바꾸자 176개가 모두 통과했습니다. 코드 문제가 아니라 휠과 OS 사이의 문제입니다.
- **수동 실행**: GitHub → Actions → CI → Run workflow. 사용자가 요청할 때만 실행합니다.
- 아래 항목은 자동 CI를 쓰던 때의 기록입니다.
- **머지 조건**: 머지 직전 PR의 head 커밋이 로컬 HEAD와 같은지 확인합니다.
- **러너 대기 취소**: macOS 러너 용량 부족으로 작업이 대기하다 취소되면 실패로 표시됩니다. 원인은 "The job was not acquired by Runner…" 주석으로 확인합니다. 이 경우 실패 표시를 둔 채 머지하지 않고, `gh run rerun <run> --failed`로 다시 돌려 통과를 확인한 뒤 머지합니다.
- **멈춘 실행 취소 금지**: 멈춘 실행을 취소하고 바로 머지하는 것은 Claude Code 권한 검사가 "CI 우회"로 막습니다. 사용자가 직접 처리하거나 재실행을 기다립니다.

### 2.4 맥 옆 Windows 머신(+WSL)에서 Windows·Linux 테스트 — 브랜치 `windows-wsl-tests`
CI를 돌리지 못해 PR #10–#13을 macOS에서만 확인하고 머지했습니다. 사용자의 맥 옆에 WSL이 있는 Windows 머신이 있어,
맥에서 명령 하나(`scripts/remote_test.sh`)로 Windows py3.10·3.13과 WSL Linux py3.10·3.13을 차례로 돌리게 했습니다.
사용법과 1회 설정은 `docs/WINDOWS_WSL_TESTING.md`에 있습니다.
- **경과**: 계획 v1 → Argon 리뷰(2.2의 괄호 실패 후 재개) → 사용자와 보안 논의 → 구현 → Argon 정적 리뷰(지적 15개, 모두 반영) → 맥에서 시험 실행.
- **방식 선택**:
  - SSH(맥 → Windows, 그 안에서 `wsl.exe`)를 택했습니다. self-hosted runner는 GitHub이 비공개 저장소 사용분 과금을
    발표했다가 2025-12에 연기했고 지금 상태를 확인하지 못해 택하지 않았습니다. 맥의 Docker는 arm64라 CI(x86_64)와 다릅니다.
  - 커밋은 `git bundle`(약 1 MB)로 보내 Windows에 GitHub 권한을 두지 않습니다. 어느 브랜치에도 없는 커밋도 보낼 수 있게
    임시 ref(`refs/coat-test/<sha>`)를 만들었다가 지웁니다(분리된 커밋으로 확인).
  - Python은 uv로 관리하고 가상환경은 실행 사이에 재사용합니다. 매 실행 `--upgrade`로 최신 휠을 설치합니다(CI와 같음).
  - Windows → WSL, py3.10 → py3.13 **순서대로** 돌립니다. GUI 테마가 OS 공용 임시 폴더에 고정 이름 파일을 써서(`gui/theme.py`)
    같은 OS의 병렬 실행이 충돌할 수 있습니다.
- **보안 (사용자 결정)**: SSH를 여는 것이 걱정된다는 사용자와 위험을 정리했습니다. 공유기 뒤라 인터넷 노출은 보통 없지만,
  Windows OpenSSH는 기본으로 비밀번호 로그인을 허용해 같은 네트워크의 기기가 대입할 수 있습니다. 결정한 대비:
  키 로그인만, 방화벽은 맥 IP·개인 네트워크만, `AllowUsers` 한 계정, 공유기 포트 포워딩·UPnP 확인, 맥 개인 키에 암호,
  **sshd 수동 시작**(테스트할 때만 켜고 끔). `setup_sshd.ps1`이 설정하고 `win_test.ps1`이 매 실행 점검해 경고합니다.
  SSH 없이 Windows에서 직접 실행하는 대안도 제시했습니다.
- **거짓 통과 막기** (Argon 지적):
  - `tests/test_gui_smoke.py`는 PySide6를 못 불러오면 통째로 건너뛰고 pytest는 성공으로 끝납니다. 그래서 건너뛴 테스트가
    하나라도 있으면 실패입니다(지금은 어느 플랫폼에서도 건너뛰는 테스트가 없음). 실패·오류 수도 JUnit XML에서 따로 봅니다.
  - PowerShell 5.1은 네이티브 명령의 실패를 넘어가고 `[int]$null`은 0이 됩니다. 종료 코드를 단계마다 받고, 비었거나 숫자가
    아닌 종료 코드 파일은 -1로 읽습니다. 결과를 맥으로 가져오지 못하면 원격이 통과했어도 종료 코드 4입니다.
  - `PYTHONUTF8`은 켜지 않습니다(켜면 인코딩을 지정하지 않은 파일 읽기 버그가 가려짐).
- **보안 설정 스크립트의 잠김 위험** (Argon 지적, 수정): 기본 `sshd_config`의 `Match Group administrators`는 관리자에게
  `administrators_authorized_keys`만 읽게 합니다. 관리자 판별이 틀려 키가 다른 파일에 들어가면 비밀번호도 꺼진 채 로그인할 수
  없습니다. 그래서 관리자 그룹 소속을 SID로 비교하고, `-User`를 필수로 했습니다(다른 관리자 자격 증명으로 승격하면
  `$env:USERNAME`이 바뀜). 프로필 폴더도 SID로 찾고, 공백 있는 계정 이름은 거부합니다. 실행 중이던 sshd는 옛 설정을 쥐고
  있으므로 끝에서 항상 멈춥니다. 원래 설정은 백업하고, `sshd -t`가 거부하면 되돌립니다.
- **그 밖의 Argon 지적 반영**: `Tee-Object`가 UTF-16으로 쓰는 문제, `wsl.exe`의 UTF-16 오류 메시지(`WSL_UTF8=1`),
  Ubuntu 24.04의 `libglib2.0-0t64` 이름 변경, SSH 세션의 PATH, Windows 가상환경의 깨진 Python, `sshd_config` 점검은
  첫 `Match` 앞의 첫 값으로, 1회 설정 파일 전달 방법, `.ps1`은 ASCII만(`tests/test_remote_scripts.py`), `.sh`는 LF(`.gitattributes`).
- **인코딩 문제 (실측으로 확인, 수정)**: `tests/test_validation_data.py`와 검증 스크립트 네 곳이 `reference.json`을 인코딩 없이 읽었습니다.

  - WSL 사용자 암호를 몰라 `wsl -u root passwd`로 다시 정했습니다(안내문에 추가).
  - 멈춘 업데이트는 `kill -TERM`을 받고도("SIGTERM received, will stop") 계산을 이어 가서, dpkg가 없고 설치 기록이 없는 것을 확인한

    CI와 같은 3 OS × 2 Python을 Actions 사용 시간 없이 처음으로 모두 확인했습니다.

**실측 RL 논문**
- **Kumar 2021** (헥사페라이트/PVA, CC BY): 그림 4를 디지털화해 계산한 피크 주파수가 실측과 약 1% 안에서 맞습니다. 대역폭은 5개 시료 중 4개가 실측과 맞습니다.

- **Duan 2010** (카르보닐철/실리콘 고무): 반례로 남겼습니다.
  - 논문의 ε·μ는 분말을 잰 값이고, RL을 잰 시트의 값이 아닙니다.
  - 실측 피크만으로 굴절률을 추정하면 |n| = 5.68 → 6.35 → 5.20으로 주파수에 따라 올라갔다 내려갑니다. 물리적으로 맞지 않습니다.
  - 그래서 검증 자료로 쓸 수 없습니다.

**교훈**
- 검증에는 **같은 시편**의 ε·μ와 **독립적으로 잰** RL이 함께 필요합니다.
- −30 dB보다 깊은 공진의 깊이는 ε·μ가 ±3%만 달라져도 −30에서 −59 dB까지 흔들립니다. 수치로 비교하지 말고 "깊은 정합"으로만 읽어야 합니다.

### 3.2 PR #1 — 굴절률(n, k) 입력과 광학 CSV
- **문제**: 광학 검증을 하면서 n, k를 ε로 손으로 변환해야 했습니다.
- **결정**:
  - n, k는 **입력·표시용 보기**로만 둡니다. 저장은 ε, μ 그대로라 저장 형식이 바뀌지 않습니다. 대가로 최적화 변수로 n을 직접 고를 수는 없습니다.
  - 변환: N = n − jk = √(εμ), ε = N²/μ. 수동 매질의 해를 고르고(k ≥ 0), 금속(ε′ < 0)도 처리합니다.
  - CSV 첫 머리글 칸으로 축을 정합니다: 주파수 / 파장(nm·µm·mm, 단위 없는 `wl`은 µm) / 파수(cm⁻¹).
  - refractiveindex.info의 두 블록 형식(`wl,n` 다음 `wl,k`)을 지원합니다. k는 **파일의 원래 축(파장)**에서 보간합니다. 주파수 축에서 보간한 첫 구현은 테스트에서 틀린 값이 나와 고쳤습니다.
  - 음수 n·k는 거부합니다.
- **미룸**: 실측 데이터를 파장 단위로 표시하는 기능(광학 모드에서)

### 3.9 PR #7 — 다중 대역·다중 각도 목표 (규격 마스크)
- **개념**: 목표 = 대역 × 각도 범위 × 편광 × 요구 RL(`BandTarget`)입니다. 최적화기는 **가장 나쁜 마진** maxᵢ(worstᵢ − goalᵢ)를 최소화합니다. 마진 ≤ 0이면 만족입니다.
- **이전 방식과 같은 결과**: 목표가 하나이고 goal = `rl_ref_db`이면 목적 함수 값이 이전 공식과 **비트 단위까지** 같습니다. 이동량이 정확히 0일 때 덧셈을 건너뛰어, 끝자리 오차가 L-BFGS-B의 수치 미분에 들어가지 않게 했습니다. 이전 공식을 독립적으로 다시 써서 `==`로 비교하는 테스트가 있습니다.
- **리뷰에서 반영**:
  - 예제와 테스트가 쓰던 `OptimizationSettings(f_min=…)` 인자와 속성을 그대로 지원합니다(첫 목표를 가리킴).
  - 평균 반사율 항은 목표별로 자기 goal로 정규화한 뒤 동일 가중으로 평균합니다. 격자가 촘촘하거나 요구가 느슨한 목표 쪽으로 치우치지 않게 하기 위해서입니다.
  - 국소 최적화의 평활화는 목표가 여러 개일 때 SMOOTH·ln N(격자 크기 편향)을 뺍니다.
  - 공차 수율은 켜진 목표 대역들의 **합집합**에서 계산합니다. 최저~최고 주파수 범위로 잡으면 두 대역 사이의 최적화하지 않은 구간이 들어가 수율이 0%로 나옵니다.
  - 꺼 둔 목표는 최적화 시작 전 재료 점검에서 제외합니다.
- **화면**: 목표 목록 + 3줄 편집기, IEEE Std 521 대역 프리셋(X = 8–12 GHz, 도파관 WR-90 8.2–12.4 GHz와 다름), 목표별 결과 행, 주파수 탭의 목표 마스크
- **예제**: "이중 대역 Jaumann (X + Ku, 경사 입사)". 두 목표 모두 −4.8 dB 마진으로 맞춰졌습니다(minimax 균형, 약 4초).
- **이 기능이 필요한 경우**: 요구 조건이 각도나 대역별로 다를 때만 의미가 있습니다. 조건이 하나면 결과는 이전과 같습니다.

### 3.10 PR #8 — 직렬 RLC 시트
- **모델**: Zs(f) = R + j(ωL − 1/(ωC)), e^{+jωt}에서 유도성 X > 0입니다. 커패시터는 선택이라, 없으면 유도성 격자가 됩니다.
  - 수직 입사 기준의 집중 소자 값으로, 모든 입사각과 편광에 같은 값을 씁니다. 단위 셀이 파장보다 충분히 작을 때만 유효하며, 툴팁과 도움말에 적었습니다.
  - R > 0, L ≥ 0, C > 0이면 수동성이 보장되고 Foster 정리도 만족합니다. R = 0은 허용하지 않습니다(공진점에서 1/Zs).
- **리뷰에서 반영**:
  - 예전의 스칼라 검사 `abs(zs) < 1e-9`는 배열에서 오류가 나 `np.any(...)`로 바꿨습니다.
  - 잘못된 값은 최적화기가 잡는 `SolverError`로 냅니다(`ZeroDivisionError`는 잡지 않음).
  - L·C 최적화 범위를 ÷10~×10으로 잡았습니다. `_Space`는 상한/하한 ≥ 100일 때만 로그 스케일을 쓰는데, 예전 기본값 ÷4~×4는 비율이 16이었습니다.
  - 해당 모델에 없는 파라미터를 읽으면 `get_param`이 `KeyError`를 냅니다. 예전에는 `float(None)`에서 아무도 잡지 않는 `TypeError`가 났습니다.
  - 공차 분석은 R·L·C를 따로 흔듭니다. Zs 전체에 같은 배율을 곱하면 f₀가 변하지 않습니다.
- **해석 테스트**:
  - 공기 중 단일 시트 Γ = −η₀/(2Zs + η₀): Γ 허수부의 부호를 직접 검증합니다.
  - 공진점에서 Salisbury 조건이면 Γ = 0
  - 40°에서 TE/TM 닫힌 식
  - 에너지 보존
  - L = 0이고 C가 없으면 상수 시트와 비트 단위로 동일
- **예제 결과**: 5–15 GHz, 두께 약 7.2 mm

  | | 최악 RL | −10 dB 대역 |
  |---|---|---|
  | Salisbury | −7.5 dB | 6.4–13.7 GHz |
  | RLC 시트 | −14.6 dB | 4.5–15.9 GHz |

- **화면 캡처로 고친 것**:
  - 속성 패널 가로 넘침 → 커패시터 체크박스의 문구를 없앰
  - PR #7에서 생긴 영문 그래프 도구 막대 넘침 → "−10 dB"로 줄이고 Back/Forward 버튼 제거
  - 층 스택 머리글 잘림 → "RLC · f₀ 8.9 GHz"로 표시

### 3.11 PR #9 — ε″·μ″ 독립 공차
- **문제**: ε와 μ에 복소수 전체로 같은 배율을 곱해서 tan δ가 변하지 않았습니다. 실제 손실 불확도(±10–30%)가 실수부(±2–5%)보다 훨씬 큰데도 이를 반영하지 못했습니다.
- **결정**:
  - 실수부와 손실에 따로 곱하는 키(`eps_re`, `eps_loss`, `mu_re`, `mu_loss`)를 추가했습니다.
  - 공차는 tan δ가 아니라 ε″·μ″의 상대 오차로 받습니다. 측정 보고 형식과 맞고, ε′ ≤ 0인 재료도 처리할 수 있습니다.
  - `None`이면 손실이 실수부를 따릅니다(이전 모델).
- **기본값과 이전 결과 보존**:
  - 새 프로젝트는 손실 10%, 실수부 5%입니다.
  - 키가 없는 기존 파일은 `None`으로 열립니다.
  - 난수를 뽑는 순서를 유지하고, 손실 난수는 그 뒤에 뽑습니다. 그래서 같은 시드에서 이전 결과와 **비트 단위로 같습니다**. 이전 알고리즘을 테스트 안에 동결해 두고 비교합니다.
- **효과** (Dallenbach, 8–12 GHz, −10 dB, 400 표본)

  | 방식 | 수율 |
  |---|---|
  | 이전 (tan δ 고정) | 62.3% |
  | 손실 10% 독립 | 60.5% |
  | 손실 20% 독립 | 49.5% |

- **알려진 근사**: 분산 재료의 실수부와 손실을 다른 배율로 곱하면 엄밀히는 Kramers-Kronig 관계와 맞지 않습니다. 대역 전체에 일정한 측정 편향을 주는 근사로 받아들였습니다. 공칭 손실이 0이면 상대 공차는 효과가 없습니다.

### 3.13 거듭제곱 법칙 재료와 Michielssen 벤치마크 — 브랜치 `power-law-benchmark`
- **계기**: `coating-experiment` 스킬을 문헌 벤치마크로 실험했습니다(Michielssen et al. 1993, 16개 재료, 5층, 2–8 GHz, ≤ 5 mm). 재료 3–8이 거듭제곱 법칙(ε′ = ε′(1 GHz)/fᵃ)이라 표 값으로 넣어야 했고, 그 결과 명세 파일이 커지고 Rozanov 판정이 `unknown`이 됐습니다.
- **결정**:
  - `PowerLawMaterial`(`kind: "power_law"`)을 추가했습니다. 인과적 모델이 아니고 f → 0에서 μ′가 발산하므로, 정적 투자율은 "알 수 없음"으로 둡니다.
  - GUI 재료 편집기에 페이지를 추가했고, 안내 문구로 "맞춘 대역 안에서만"이라고 적었습니다.
  - 모르는 재료 종류가 든 파일을 이전 앱은 경고 없이 다르게 계산하지 않고 오류로 거부하므로 `SCHEMA_VERSION`은 올리지 않았습니다(4장 원칙).
- **조사와 검증**:
  - agy가 문헌을 찾았지만, 재료 8의 ε″를 ACES 2024 논문의 오타(16)대로 보고했습니다. 사용자가 올려 준 원문 2곳(Asi & Dib 2010, Kankılıç & Karpat 2023)은 모두 6입니다. 출처 하나로는 잡을 수 없는 오류였습니다.
  - 사용자가 올린 4개 중 1개(`10081704.pdf`)는 같은 저자의 다른 논문(필터 설계)이었습니다.
  - Asi & Dib의 설계 5개는 그 논문의 0.5 GHz 격자에서 0.05 dB 안으로 재현됩니다. 이는 재료표와 엔진을 함께 검증합니다.
  - BESOA(2023)와 MIGRO(2024)가 보고한 값은 어느 격자에서도 0.12–0.19 dB 나쁘게 나와 "재현되지 않음"으로 기록했습니다.
  - ACES 2024는 0.5 GHz 격자 결과와 0.1 GHz 격자 결과를 한 표에서 비교했습니다.
- **스킬 실험 결과**: `coating-cli optimize --restarts 3`을 3회 돌려 −25.927 dB, 4.996 mm를 찾았습니다. 재현되는 문헌 최선(Asi & Dib 표 4, −25.884 dB)보다 0.04 dB 좋습니다.
  - 처음에는 표 2만 보고 "0.26 dB 좋다"고 보고했다가, 표 4를 확인한 뒤 바로잡았습니다.

- **두 번째 벤치마크**(Amaya & Correa 2013, 3층, 0.85–5.4 GHz): 사용자가 원본 PDF의 글꼴 인코딩을 고쳐 다시 올려 줬습니다.
  - 수정본의 숫자는 원본의 깨진 글자를 숫자로 대응시켜 대조했고, 일치했습니다.
  - 설계 3개가 0.01 dB 안으로 재현됩니다. 재료 3·4를 쓰는 설계라, 그 논문이 싣지 않은 거듭제곱 지수까지 독립적으로 확인해 줍니다.
  - 그 논문의 표 1은 재료 9–16의 열 이름이 잘못 붙어 있습니다(값은 μm·fm²·10⁻³, μm·fm·10⁻²).
  - 수정본에서 그림 2 자리에 들어간 요약 문장은 원문이 아니라 판단해 인용하지 않았습니다.

### 3.16 Goudos 2009 원문 대조 — 브랜치 `goudos-literature`
- 사용자가 Goudos 2009 원문(*Int. J. RF Microwave CAE* 19(3), 364–372, [doi:10.1002/mmce.20357](https://doi.org/10.1002/mmce.20357))을 구해 줬습니다. Michielssen 1993 원문은 구하지 못했습니다.
- **재료표**: 표 I의 16개 재료가 `reference.json`과 모두 일치합니다. 재료 8의 ε″(1 GHz) = 6이 세 번째 출처로 확인됐습니다. 재료 9–16의 완화형 식도 같습니다.
- **잘못 붙인 출처를 바로잡음**: `designs`의 "SADE (DE)" 행(−25.485 dB)에 "Goudos 2009에서"라고 적어 두었는데, 그 논문에 없는 설계였습니다.
  - Asi & Dib가 Tvrdík 등의 경쟁형 SADE 라이브러리(그 논문의 참고문헌 9)로 직접 돌린 결과입니다.
  - Goudos가 쓴 알고리즘은 Brest 등의 자기 적응 DE(jDE)이고, 같은 문제(2–8 GHz, ≤ 5 mm)에서 그 논문의 최선은 −24.75 dB입니다.
  - 행 이름을 "SADE (Asi & Dib run)"로 바꿨습니다.
- **Goudos 자신의 설계** (주파수 격자는 논문에 없어 0.1 GHz로 계산):
  - HF1(5.000 mm)은 −24.73 dB로, 문헌 −24.75 dB와 일치합니다. `must_reproduce`로 넣었습니다.
  - DES2(0.5–8 GHz)는 −20.24 dB로, 문헌 −20.26 dB와 일치합니다. 대역이 달라 참고문헌 메모에만 적었습니다.
  - HF2(2.57 mm)는 0.07 dB 차이가 나 재현 기준(0.05 dB)을 넘습니다.
  - DES1(3–6 GHz, 0–10°, TE+TM)은 표대로 넣으면 −13.2 dB로 전혀 맞지 않습니다. 3층을 재료 6으로, 4층을 재료 15로 바꾸면 −26.1 dB(문헌 −25.98)가 됩니다. 하지만 2,560개 조합에서 가장 좋은 것을 고른 것이므로 오식 가설일 뿐이며, 검증하지 않음으로 기록했습니다. (2026-11-09에 아래와 같이 검증했습니다.)
    - **결론**: Table VIII의 인쇄 오류는 확인했습니다. 3층 = 재료 6, 4층 = 재료 15로 고치는 가설은 강하게 지지되지만, 논문이 그린 설계와 같다고 증명하지는 못했습니다. `must_reproduce`로 넣지 않습니다.
    - **인쇄 오류의 근거**: 인쇄 구성은 재료 14/6/5/14/2, 두께 0.420/1.881/1.743/1.497/0.456 mm입니다. 계산하면 대역 내 최댓값이 −13.2 dB이고 최저점은 7.9 GHz입니다. 같은 논문의 Fig. 6은 최저점이 약 2.3 GHz이고 3–6 GHz에서 약 −26 dB입니다.
    - **가설의 근거**: 인쇄 두께에서 재료 조합 16⁵개를 모두 계산했습니다. −25.98 dB의 0.15 dB 안에 드는 것은 6개뿐이고 모두 14/6/6/15/x(x = 1, 2, 6, 7, 8, 12)입니다. 재료를 1~2개 고치는 2,325개 중에서는 14/6/6/15/2 하나뿐이고, 1개만 고치면 최고 −24.99 dB입니다. 5층은 구별되지 않으므로 인쇄된 2를 유지합니다. 눈으로 읽은 Fig. 6의 TE 곡선과는 1 GHz(계산 −11.5, 그림 약 −11)와 10 GHz(−14.8, 약 −14.4)에서 맞습니다.
    - **설명되지 않는 차이**: 계산값은 −26.10 dB로 0.12 dB 좋고, 주파수·각도 격자와 두께 반올림으로는 메워지지 않습니다. Fig. 6의 최저점(2.27 GHz, 약 −52 dB)과 계산(2.45 GHz, −33.5 dB)이 다르고, TE 0°와 10° 곡선의 위아래도 반대입니다.
    - **논문 식의 문제**: Fig. 6에서 TE 0°와 TM 0°가 서로 다른데, 수직 입사에서는 같아야 합니다. 식 (6)의 TM 종단 r = −1은 그 부호 규약에서 PMC 뒷면에 해당합니다. 고친 재료로 그렇게 계산하면 TM이 1·2 GHz에서 그림에 가까워지지만(−5.8·−14.6 dB, 그림 약 −5.2·−15), 대역 내 최댓값은 −22.7 dB라 −25.98 dB를 설명하지는 못합니다.
    - 같은 조건의 자유 탐색(재료 + 두께, 층당 2 mm, 합 6 mm 이하)에서는 올바른 물리로 −32.46 dB, 식 (6) 그대로면 −27.58 dB까지 나옵니다. 논문의 −25.98 dB는 전역 최적이 아닙니다. 계산 스크립트는 저장소에 넣지 않았습니다.
- **Michielssen GA 설계의 재인쇄본**: HF1(5.244 mm)은 −24.02 dB로, 인쇄값 −23.5보다 0.5 dB 좋게 계산됩니다. HF2는 −19.68 dB(인쇄 −19.8)입니다. 원문 없이는 이유를 알 수 없어 "재현되지 않음"으로 보고만 합니다. (3.25에서 원문으로 확인했습니다.)
- **층당 2 mm 제한**: Goudos와 Asi & Dib 모두 Michielssen을 따라 층당 최대 두께를 2 mm로 둡니다. 3.14의 문제 B에 둔 같은 가정을 뒷받침합니다(문제 B 논문 자체에는 적혀 있지 않음).
- 검증 예제의 확인은 13/13 통과합니다.

### 3.17 미뤄 둔 작업 네 가지 — 브랜치 `deferred-features`
6장에 남아 있던 항목 중 네 가지를 처리했습니다. 기능마다 커밋을 나눴습니다.
- **실수부·손실 오차의 상관계수 ρ** (`tolerance.loss_correlation`, −1…1, 기본 0)
  - 3.11에서는 ε″ 오차를 ε′ 오차와 독립으로 뽑았습니다. 실제로는 충전재 함량처럼 둘을 함께 움직이는 원인이 흔합니다.
  - 정규 분포: 표준화한 값에서 z = ρ·z′ + √(1−ρ²)·z″로 섞습니다. 손실 오차의 σ는 그대로이고 상관계수는 정확히 ρ입니다.
  - 균일 분포: 같은 섞기를 가우시안 코풀라로 해서 두 분포가 그대로 균일합니다. 피어슨 상관계수는 (6/π)·asin(ρ/2)로, ρ와 0.02 안에서 다릅니다.
  - ρ = 0이면 섞기를 건너뛰어 이전 결과와 비트 단위로 같습니다. 이를 확인하는 테스트는 난수 순서를 직접 다시 뽑아 비교합니다.
  - 난수 생성을 `sample_factors()`로 분리해, 풀이 없이 통계만 시험합니다(4000표본에서 상관계수·σ·균일성).
  - 이전 앱은 이 키를 무시하고 다른 수율을 내므로 `SCHEMA_VERSION`을 5로 올렸습니다(4장 원칙).
- **입사각·맵 탭의 목표 마스크**
  - 입사각 탭: 각도 스윕 주파수가 대역 안에 드는 목표를 각도 범위에 걸친 요구 수준 선으로 그립니다(각도가 하나면 표시점).
  - 맵 탭: 목표마다 대역 × 각도 상자(한 변이 한 값이면 선·점)와 "T번호 요구값" 라벨을 그립니다.
  - 맵 탭 테두리 색: 상자 안 맵 격자 셀이 모두 요구를 만족하면 초록, 하나라도 못 미치면 빨강, 상자 안에 격자 셀이 없으면 회색입니다. 맵 격자는 목표 격자보다 성기므로 최적화기 판정이 아니라 눈으로 보는 단서이며, 툴팁에 적었습니다.
  - 화면 캡처에서 0° 선 목표의 라벨이 x축 눈금과 겹쳐, 선·점 목표는 라벨을 위쪽에 두도록 고쳤습니다.
- **비교 곡선의 `.coat` 저장** (3.8 결정 2를 바꿈)
  - 저장할 때 화면의 비교 곡선(이름, 종류, 색 슬롯, 표시 여부, 설계 스냅샷 또는 측정값)을 `references`로 씁니다.
  - 비교 곡선이 저장된 파일을 열면 그 곡선을 보여 줍니다. 저장된 곡선이 없는 파일을 열면 화면의 곡선을 유지합니다. 다른 파일의 설계와 비교하던 기존 사용 방식을 지키려는 것입니다.

  - 이전 파일은 곡선 없이 열립니다. 이전 앱은 스키마 5를 거부하므로 곡선을 조용히 잃지 않습니다.
- **Touchstone(.s1p) 입출력과 보고서 내보내기**
  - 파일 → Touchstone 내보내기, `coating-cli solve --touchstone PATH`: 주파수 스윕의 S11을 편광 하나로 씁니다. 사입사에서는 편광을 묻거나(GUI) `--pol`을 요구합니다(CLI).

### 3.18 층별 상관계수 ρ — 브랜치 `per-layer-rho`
3.17의 ρ는 프로젝트 전체에 하나였습니다. 층마다 재료와 제조 공정이 다르면 실수부·손실 오차가 함께 움직이는 정도도 다르므로, 층별로 바꿀 수 있게 했습니다.
- **저장 위치**: 다른 층별 공차와 같은 `tolerance.per_layer[uid]`에 `loss_correlation` 키를 둡니다. 값이 없으면 기본 ρ를 씁니다(`tolerance_for`). 다른 키는 상대 공차지만 이 키는 −1…1 계수입니다.
- **표본 추출**: `sample_factors`가 층마다 ρ를 읽습니다. 난수 순서는 바꾸지 않았으므로, 기본값과 같은 ρ를 층에 지정하면 지정하지 않았을 때와 비트 단위로 같은 표본이 나옵니다. 층 ρ = 0이면 그 층만 독립 표본으로 돌아갑니다. 둘 다 테스트로 확인합니다.
- **범위 검사**: 층 ρ가 −1…1을 벗어나면 `run_tolerance`는 `ValueError`, CLI 설계 명세는 `invalid_spec`(`tolerance.per_layer[i].loss_correlation`)입니다. GUI 표에서는 입력을 거부하고 칸을 되돌립니다.
- **GUI**: 층별 공차 표에 ρ 열을 μ″와 시트 사이에 넣었습니다(8열). 슬래브 층에만 쓸 수 있고 값은 백분율 없이 그대로 표시합니다. 다른 층별 공차처럼 실행 취소할 수 있습니다(`per_layer`가 `model_state`에 들어 있음).
  - 캡처해 보니 열이 하나 늘면서 층 이름이 "1. …"로 잘렸습니다. 왼쪽 패널의 최소 폭을 400 → 440 px(처음 폭 440 → 480 px)로 늘렸고, 이름 칸에 전체 이름을 툴팁으로 붙였습니다.
- **CLI**: 명세의 `tolerance.per_layer[]` 항목에 `loss_correlation`을 쓸 수 있습니다. 명세 버전은 그대로입니다(키 추가만 있음).
- **저장 형식**: 이전 앱은 이 키를 무시하고 다른 수율을 내므로 `SCHEMA_VERSION`을 6으로 올렸습니다(4장 원칙). 이전 파일에는 이 키가 없어 결과가 그대로입니다.
- **보고서**: 공차 문단은 기본 ρ만 적고 "층별 지정값은 나열하지 않음"이라고 밝힙니다. 다른 층별 공차와 같은 처리입니다.
- **검증**: 테스트가 199개에서 201개로 늘었고, py3.10·3.13에서 모두 통과합니다.

### 3.19 목표 각도 격자의 수율 — 브랜치 `per-layer-rho`
3.15의 꼭짓점 수율은 목표마다 각도 범위의 양 끝만 봤습니다. 최적화기는 목표의 각도 격자(`BandTarget.grid()`, `n_angle`점)로 판정하므로, 수율도 같은 각도에서 볼 수 있게 했습니다. 계획 v1을 Argon에게 리뷰받았고(2.2), 지적 15개의 근거를 모두 직접 확인한 뒤 계획 v2로 고쳤습니다.
- **엔진** `tolerance.run_tolerance_targets(project, f, mode="corners"|"grid", n_angle=None, …)`:
  - 표본은 한 번만 뽑고, 표본마다 **서로 다른 각도마다 한 번** 풉니다(목표에 있는 편광만). 그래서 모든 행이 같은 표본을 보고 결합 수율이 정확합니다.
  - 각 행은 그 각도·편광의 `run_tolerance`와 비트 단위로 같습니다. 처음 계획은 모든 각도를 한 번에 푸는 것이었는데, Argon이 CPU에 따라 ULP 차이가 날 수 있다고 지적했습니다. 이 맥에서는 예제 7개 모두 같았지만 Windows·Linux는 확인할 수 없어, 같음이 구조적으로 보장되는 각도별 풀이를 택했습니다. Dual-band 예제(꼭짓점 6개)는 이전 구현의 0.05 s에서 0.03 s로 오히려 빨라졌습니다(같은 각도의 TE·TM을 한 번에 풂).
  - 꼭짓점 모드(`run_tolerance_corners`는 이제 이 함수를 부르는 얇은 함수)의 결과는 이전 구현과 비트 단위로 같습니다(예제 7개 확인, 테스트는 행마다 `run_tolerance` 직접 호출과 비교).
  - `n_angle`이 2 미만인데 각도 범위가 있는 목표는 양 끝으로 대신하고 `fallback_targets`에 적습니다. 최적화기는 이때 하한 각도만 보지만, 꼭짓점 평가보다 덜 엄격해지지 않게 하려는 선택입니다. 각도 범위가 없는 목표는 각도 하나입니다(중복 행 없음).
  - 중단해도 표본은 최소 1개 풉니다(0개면 공칭 설계로 대체되어 수율이 틀림). 진행 콜백은 표본 단위 `(done, total)`입니다.
  - 목표 편광에 `TE`·`TM` 외의 값(손으로 고친 파일의 `avg`)이 있으면 최적화기처럼 거부합니다.
- **CLI** `tolerance --angle-grid [--n-angle N]`: 출력은 `--corners`와 같은 모양에 `angle_mode`가 붙습니다. `--n-angle`은 각도 범위가 있는 목표에만 적용합니다(CLI 전용, 최종 수율을 최적화보다 촘촘하게 확인하는 용도).
- **GUI**: "목표의 모든 꼭짓점 평가" 확인란을 "평가 각도" 콤보 상자(한 각도 / 목표별 각도 범위의 양 끝 / 목표별 각도 격자)로 바꿨습니다. 저장하지 않는 화면 상태라 스키마는 그대로입니다. 행이 많아져 그래프 아래에는 목표별 최저 수율만 쓰고 전체 행은 툴팁에 둡니다. 보고서도 격자 모드에서는 목표별 최저 수율만 적습니다.
  - 캡처해 보니 그래프 제목("Joint yield … over 10 angle-grid points (60 samples)")의 끝이 잘렸습니다. 3.18에서 왼쪽 패널을 넓힌 탓에 꼭짓점 제목도 같은 폭에서 잘릴 수 있어, 제목을 줄바꿈하게 했습니다(영문·한글 확인).
- **사용자 결정** (계획 v1의 열린 질문):
  - GUI와 CLI를 옵션 없이 실행하면 지금처럼 한 각도입니다. 격자는 GUI 콤보 상자와 `--angle-grid`로 고르고, 플레이북·스킬은 `--angle-grid`를 권합니다.
  - 격자를 더 촘촘히 하는 `--n-angle`은 CLI에만 둡니다. GUI는 목표의 `n_angle`을 그대로 씁니다.
  - Argon이 찾은 기존 버그 4개는 이번 작업에서 함께 고칩니다(모두 이번에 손대는 코드 안에 있었음).
  - CLI 진행 이벤트는 표본 단위 하나로 통일합니다(꼭짓점 단위 키는 계약에 없었음).
- **함께 고친 기존 버그** (Argon 지적, 모두 재현 후 수정):
  - GUI: 꼭짓점 결과를 띄운 채 목표를 끄거나 지우면 공차 그래프가 `IndexError`로 그려지지 않았습니다. 이제 사용 중인 목표가 바뀌면 다중 각도 결과를 버립니다(`TolerancePanel.settings_changed`).
  - CLI: `--corners`가 `-o`, `--format csv`, `--angle-deg`, `--pol`을 조용히 무시했습니다. 단일 각도 `tolerance`도 JSON `-o`를 무시했습니다. 이제 `-o`는 JSON 결과를 파일에 쓰고(봉투에는 요약), `--format csv`는 가장 취약한 행의 곡선(GUI 내보내기와 같음)을 씁니다. `--angle-deg`·`--pol`과 `--angle-grid` 없는 `--n-angle`은 사용 오류(종료 코드 2)입니다.
  - CLI: `--corners`의 결과에 최상위 `target_db`가 없어 실험 기록에 늘 `null`이 남았습니다. 이제 `--target-db` 값(없으면 `null`, 행마다 그 목표의 goal)을 쓰고 기록에 `angle_mode`도 남깁니다. CLI_PLAN 부록 B의 예시도 실제 출력에 맞췄습니다.
  - CLI: `--corners --progress`에서 마지막 진행 줄이 두 번 나왔습니다. 이제 표본 단위 진행 한 종류만 냅니다(`corner`·`n_corners` 키는 없어짐).
- **안쪽 각도가 더 나쁜 실례는 찾지 못했습니다.** 예제 7개(각도 범위가 없는 목표는 0–60°로 넓혀 봄), 최적화한 Dual-band, Ku 목표를 0–60°·5점으로 넓혀 시드 3개로 최적화한 설계 모두에서, 목표 대역 최악 RL은 각도에 따라 단조이거나 가운데가 가장 좋은 U자였습니다(예: 0° −11.5, 30° −15.9~−20.4, 60° −11.5 dB). 이런 설계에서는 격자와 꼭짓점의 결합 수율이 같습니다(최적화한 Dual-band: 둘 다 72.5%). 격자 모드는 이 가정을 확인하는 수단이며, 격자 점 사이 각도는 여전히 보지 않습니다.
- **검증**: 테스트가 201개에서 207개로 늘었고, py3.10·3.13에서 모두 통과합니다.

### 3.20 보고서의 공차 밴드 그래프 — 브랜치 `per-layer-rho`
6장에 미뤄 둔 "보고서의 공차 밴드 그래프"를 처리했습니다. PDF 직접 출력은 계속 미룹니다.
- **출발점에서 찾은 문제**: GUI는 마지막 공차 결과를 보고서에 넘기는데, 공차 설정(공차 %, 백분위, 목표 RL)을 바꿔도 결과가 남습니다. 그래서 보고서의 설정 문단과 GUI 그래프의 범례·목표선이 결과를 낸 설정이 아니라 **현재 설정**을 보여 줄 수 있었습니다(재현함). 그래프를 넣으면 더 눈에 띄므로 같이 고쳤습니다.
- **경과**: 계획 v1 → Argon 리뷰(2.2, 지적 14개, 모두 근거 확인, 틀린 지적 없음) → 계획 v2 → 구현. 계획 v1의 "정해야 할 것" 세 가지도 리뷰에 넣어 의견을 받았습니다.
- **사용자 결정**:
  - 설정 불일치는 **결과에 실행 당시 설정을 저장**해서 고칩니다. 설정을 바꾸면 결과를 버리는 대안은 표본 수만 바꿔도 결과가 사라지고, 3.19에서 넣은 테스트(표본 수 변경 뒤에도 결과 유지)와도 어긋납니다(Argon 근거).
  - 목표 꼭짓점·각도 격자 결과는 보고서에 **목표마다 최저 수율 행을 하나씩** 그립니다. 목표마다 대역·목표값·취약 각도가 달라 한 그래프로는 보여 줄 수 없습니다.
  - Argon이 찾은 기존 버그 2개를 함께 고칩니다.
- **엔진** (`tolerance.py`):
  - `ToleranceResult`에 `settings`(실행 설정의 깊은 사본)와 `band`(수율 판정에 실제로 쓴 구간 목록)를, `CornerResult`에 `settings`를 추가했습니다. 기본값은 `None`이고, 손으로 만든 결과는 `result_settings`·`result_band`가 현재 프로젝트 값으로 대신합니다.
  - 각도별 결과의 행은 **그 행의 각도·편광·목표값으로 바꾼** 사본을 가집니다. 엔진의 단일 각도 설정을 그대로 넣으면 실제로 평가하지 않은 각도가 기록된다는 Argon 지적을 반영했습니다. 그래서 행의 설정은 그 점에서 `run_tolerance`를 직접 부른 결과의 설정과 같습니다(테스트로 확인).
  - 사본은 `ToleranceSettings.from_dict(to_dict())`로 만듭니다. 엔진을 직접 부르는 곳(테스트, 보고서)은 프로젝트를 복사하지 않으므로, 얕은 복사로는 층별 공차 dict가 공유됩니다.
  - 판정 구간은 들어온 형태(`None`, `(lo, hi)`, 구간 목록)와 상관없이 구간 목록으로 저장합니다. 대역이 없거나 대역 안에 격자 점이 없어 전체 주파수를 쓴 경우는 전체 구간으로 기록합니다.
- **그리기 공유**: `report.draw_tolerance_band`를 GUI 공차 탭과 보고서가 함께 씁니다(백분위 음영, 중앙값, 공칭, 목표선, 판정 구간 음영).
  - `report.py` 안에 두어 AGENTS.md의 모듈 목록은 그대로입니다. GUI 테마 색 클래스는 PySide6를 불러오는 모듈에 있어 색은 dict로 넘깁니다.
  - 로그 축은 `set_xlim` 전에 바꿔야 해서 인자로 받습니다. 격자선은 GUI는 테마가, 보고서는 직접 그립니다.
  - GUI 그래프도 이제 결과에 저장된 목표값·판정 구간·백분위를 씁니다. 각도별 결과에서 목표를 현재 프로젝트에서 다시 찾지 않으므로, 3.19의 `IndexError` 같은 문제가 구조적으로 생기지 않습니다.
  - 꼭짓점 이름표 함수 `corner_label`도 Qt 없는 `report.py`로 옮겼습니다.
- **보고서**: 단일 각도 결과는 그래프 1개, 각도별 결과는 목표마다 1개(최대 6개, 넘으면 **수율이 낮은 목표부터** 고르고 목표 순서로 배치, 생략 안내 문구)입니다. 제목에 목표·각도·편광·수율·표본 수를 넣습니다. 그래프는 RL 부호 설정, 한글 글꼴, 로그 축을 따릅니다.
- **중단 표기**: "표본 M개 중 N개에서 중단"을 GUI 그래프 제목과 보고서 본문·그래프 제목에 똑같이 씁니다. M은 저장된 설정의 표본 수입니다.
- **함께 고친 기존 버그** (Argon 지적, 재현 후 수정):
  - 마지막 표본을 계산하는 중에 중지하면 표본을 모두 풀었는데도 "중단됨"이 됐습니다. CLI 콜백만 이 경우를 막고 있었습니다. 엔진(`run_tolerance`, `run_tolerance_targets`)에서 마지막 표본 뒤의 중지 요청은 무시합니다.
  - 시드가 무작위면 보고서에 `seed None`(한글 `시드 None`)이 찍히고 분포 이름이 번역되지 않았습니다. 이제 "무작위", "정규"·"균일"로 씁니다.
- **Qt 경계 테스트 추가**: GUI가 `report.py`에서 그리기 함수를 가져오므로, 보고서를 만들 때 PySide6를 불러오지 않는지 별도 프로세스로 확인합니다(지금까지는 CLI만 확인했음, Argon 지적).
- **검증**: 테스트가 207개에서 212개로 늘었고, py3.10·3.13에서 모두 통과합니다. 영문(음수 RL)·한글(양수 RL) 보고서의 그래프와 GUI 공차 탭을 캡처해 확인했습니다. GUI 그래프는 공유 함수로 바꾼 뒤에도 이전 캡처와 같았습니다.

### 3.21 스펙트럼 축 표시 단위 (주파수·파장·파수) — 브랜치 `wavelength-units`
6장의 "광학 데이터의 파장 단위 표시"(PR #1에서 미룸)를 처리했습니다. 엔진은 Hz로 계산하는데 화면은 어디서나 GHz로 고정돼 있어,
광학 설계에서 550 nm가 545,077 GHz로 보였습니다(CSV는 PR #1부터 파장·파수 축을 읽었지만 표시는 GHz뿐).
- **경과**: 코드 조사 → 계획 v1 → Argon 리뷰(지적 14개, 코드 근거 모두 확인, 1개는 일부 틀림 — 5.2) → 계획 v2 → 구현 → 캡처 확인.
- **단위와 저장**: 프로젝트 설정 `SweepSettings.spectral_unit` — GHz(기본), THz, 진공 파장 µm·nm(λ₀ = c/f), 파수 cm⁻¹.
  해석 설정의 "스펙트럼 축" 콤보 상자에서 고르고 프로젝트에 저장합니다(광학 프로젝트는 nm, 레이더는 GHz로 열림).
  - **표시 전용**이라 결과가 바뀌지 않으므로 `SCHEMA_VERSION`을 올리지 않았습니다(4장 원칙. 이전 앱은 키를 무시하고 GHz로 보여 줌).
    풀이 캐시 키(`SweepSettings.key()`)에도 넣지 않았습니다. 알 수 없는 값이 든 파일은 GHz로 읽습니다.
  - CLI 수치(`f_ghz` 등)는 계약이라 GHz 그대로이고, 명세에 선택 키 `sweep.spectral_unit`으로 왕복 보존합니다(Argon 지적).
- **적용 범위**: 그래프 x축·커서·데이터 내보내기(주파수, 맵, 층별 흡수, 재료 물성, 공차, Smith 표, 피팅 대화상자), 목표 마스크·맵 목표 상자·비교 곡선,
  입력칸(스윕 시작·끝, 각도 스윕 위치 — 해석 설정과 각도 탭 막대 둘 다, 최적화 목표 대역, 공차 수율 대역), 상태 표시줄의 최고 RL,
  목표 목록, 속성 패널의 Zs(f), 재료 편집기(측정 데이터 표·범위·미리보기), 진단 문구, HTML 보고서.
- **GHz로 남긴 것**(결정): 재료 모델 파라미터 f₀·γ(γ는 대역폭이라 c/γ로 바꾸면 물리적으로 틀림 — Argon 근거), PowerLaw의 1 GHz 기준,
  RLC 시트 f₀, 레이더 대역 프리셋, Touchstone(.s1p는 Hz 형식), CLI 수치. 파장 등간격 격자·MHz·앱 기본 단위 환경설정은 넣지 않았습니다.
- **변환과 배치**: 변환식은 `core/units.py`(`to_spectral`/`from_spectral`/`spectral_bounds`, f ≤ 0은 오류), 표시용 도우미(축 이름, "550 nm",
  범위 문구, CSV 머리글, 오름차순 축)는 Qt 없는 `spectral.py`(보고서가 함께 씀), 입력칸 묶음은 `gui/spectral.py`.
  `fmt_num`은 `spectral.py`가 쓰려고 `core/units.py`로 옮기고 `gui/fmt.py`에서 다시 내보냅니다.
- **파장이 주파수와 반대로 가는 문제** (Argon 지적 대부분):
  - 기존 `set_xlim(x[0], x[-1])`는 내림차순 파장에서 축을 뒤집습니다. 축은 항상 오름차순으로 두고, 맵(`pcolormesh`·등고선)과 흡수(`stackplot`)는
    x와 데이터를 오름차순으로 뒤집어 넘깁니다.
  - 대역(목표 마스크, 맵 상자, 공차 대역, 보고서)은 변환 뒤 정렬합니다. 맵 상자의 셀 선택은 주파수로 하고 그리기만 표시 단위로 합니다.
    단일 주파수 목표(f_min = f_max)는 그대로 됩니다.
  - 입력칸 한 쌍은 파장에서 시작(짧은 파장) 칸이 f_max, 끝 칸이 f_min입니다.
- **부동소수점 왕복 드리프트 방지** (Argon 지적): 패널의 `_commit`은 관계없는 컨트롤을 바꿔도 모든 입력칸을 다시 읽어 저장합니다. 파장 변환
  (c/(c/f))을 거치면 끝자리가 바뀌어 파일이 "수정됨"이 됩니다. `SpectralInputs`가 표시할 때의 Hz를 기억하고 숫자가 바뀐 칸만 변환하므로,
  손대지 않은 값은 비트 단위로 그대로입니다(테스트로 확인). 공차의 사용자 대역을 켤 때도 표시 중이던 Hz(목표 대역)가 그대로 들어갑니다.
  이 방식은 GHz에서도 같은 효과가 있습니다.
- **그 밖의 Argon 지적 반영**: 입력칸 범위를 1e-9 ~ 1e15로(2–18 GHz는 약 1.7e7–1.5e8 nm), 커서는 이미 표시 단위인 축 좌표를 다시 변환하지 않음,
  설정 변경 시 흡수·물성·Smith 뷰도 다시 그림(최적화 패널은 단위가 바뀔 때만 새로 그려 자체 편집을 방해하지 않음), 재료 편집기가 단위 변경을 받음,
  Smith 설명을 실제 양 끝 값("● 2 GHz, ■ 18 GHz")으로, 진단 문구 4종(측정 범위 밖, 수동성 위반 ×2, 스윕이 데이터 밖)을 단위에 맞춰 표시(문제 객체의
  인자와 CLI 메시지는 GHz 그대로), 데이터 내보내기 첫 열을 유효숫자 10자리로(파장 왕복 시 중복 여유).
- **내보낸 CSV 다시 읽기**: 머리글 `f [GHz]`·`f [THz]`·`lambda [um]`·`lambda [nm]`·`nu [cm-1]`을 기존 측정 곡선 읽기(`csvio._abscissa`)가 모두
  알아보는 것을 계획 단계에서 실행해 확인했고, 다섯 단위 모두 왕복 테스트로 고정했습니다.
- **캡처로 고친 것**: 해석 설정의 각도 스윕 "주파수" 라벨이 nm 값 옆에 남아 있어 단위에 따라 주파수·파장·파수로 바꿨습니다.
  재료 편집기의 측정 데이터 표가 파장에서 800 → 550 → 400 nm(주파수 순서)로 보여, 읽기 전용 표를 표시 단위 오름차순으로 바꿨습니다.
- **확인 예**: BK7 위 MgF₂ λ/4 반사방지막(550 nm 설계)을 400–800 nm로 보면 최소 반사가 550 nm 부근 약 −19 dB(R ≈ 1.26%, 3.1절 엔진 검증의 해석해와 같은 값)이고,
  맵의 목표 상자가 450–650 nm × 0–30°에 정확히 그려집니다(영문·한글 캡처).
- **새로 미룬 것**: 광학 박막 두께 단위(3.22에서 처리). ~~두께 입력의 최소가 1e-4 mm(100 nm)이고 소수 4자리라 수십 nm 박막을 다루기 어렵습니다(Argon 지적, 6장).~~
  **정정(3.22)**: 이 문장은 틀렸습니다. 리뷰의 주장을 코드로 확인하지 않고 옮겼습니다. 두께 칸은 최소 0, 소수 15자리라 50 nm도 들어갑니다.
  실제 문제는 `9.9640e-05 mm`처럼 읽고 써야 하는 불편이었습니다(5.2).
- **검증**: 테스트가 215개에서 229개로 늘었고(변환·저장·CLI·진단·보고서·내보내기 왕복 12개, GUI 2개), 맥 py3.10·3.13에서 모두 통과합니다.

### 3.22 두께 표시 단위 (mm·µm·nm) — 브랜치 `thickness-units`
3.21에서 미룬 광학 박막 두께 단위를 처리했습니다. 3.21과 같은 흐름(코드 조사 → 계획 v1 → Argon 리뷰 → 확인 → 계획 v2 → 구현 → 캡처 → 원격 검증)입니다.
- **출발점 정정**: 3.21과 6장에 적은 "두께 입력 최소 100 nm·소수 4자리"는 틀렸습니다. 코드 조사에서 확인해 보니 속성 패널의 두께 칸은
  `SciSpinBox(minimum=0.0, maximum=1e6)`·소수 15자리라 50 nm(`5e-05 mm`)가 그대로 들어가고, 층 표에는 편집 위젯이 없습니다.
  문제는 "입력 불가"가 아니라 99.64 nm를 `9.9640e-05 mm`로 읽고 써야 하는 불편이었습니다. 3.21을 바로잡고 5.2에 기록했습니다.
- **단위와 저장**: 프로젝트 설정 `SweepSettings.length_unit` — mm(기본)·µm·nm. 해석 설정의 "두께 단위"에서 고릅니다.
  - 3.21의 `spectral_unit`과 같은 방식: 표시 전용 → 스키마 6 유지, 풀이 캐시 키에 넣지 않음, 알 수 없는 값은 mm, CLI 명세 선택 키로 왕복.
  - 저장 위치는 Argon과 같은 의견으로 `SweepSettings`(안 A). 최상위 `display` 절로 옮기면(안 B) `.coat`와 CLI 명세 양쪽에 옛 위치 읽기가 필요해집니다.
  - **스펙트럼 단위와 독립**(자동 연동 없음): 파장 축(nm)에서 두께를 µm로 보는 경우도 흔하고, 설정을 바꿀 때 다른 단위가 바뀌면 예측하기 어렵습니다.
- **적용 범위**: 속성 패널 두께 칸, 층 스택 표, 단면의 총 두께, 상태 표시줄, 최적화 패널(총 두께 기준값·두께 상한 칸, 변수 표의 현재값·범위,
  변수 추가 목록, 결과 표의 총 두께·두께 변수), HTML 보고서(층 표, 요약의 총 두께).
  **mm 그대로**: CLI 수치(`thickness_mm`), Rozanov 문구(μs·d, PEC 뒷판 레이더 전용이고 CLI `check` 인자와 묶임), 밀도·면밀도.
- **CLI 계약 보호** (내 확인): 최적화 변수 경로의 단위(`param_unit`)는 "mm" 그대로이고 `DISPLAY_SCALE`도 넓히지 않았습니다. CLI의 `invalid_spec`
  오류가 `allowed=list(DISPLAY_SCALE)`로 단위 목록을 내보내기 때문입니다. GUI만 `lengths.display_unit`으로 "mm"를 프로젝트 단위로 바꿔 보여 줍니다.
  CLI 명세에 잘못 쓴 `thickness_nm` 키도 이제 "지원하지 않는 단위"로 알려 줍니다(전에는 `thickness_mm`가 없다고 나옴).
- **Argon 리뷰가 바꾼 것** (지적 9개, 코드로 모두 확인. 이번에는 계획의 열린 질문 4개에 번호대로 답함):
  - 입력칸 상한 1e6 때문에 nm에서 1 mm 이상(기본 기준값 5 mm, 상한 10 mm)이 1 mm로 잘리고 저장까지 될 수 있었습니다 → 범위 0–1e15.
  - 총 두께 기준값·상한 칸도 관계없는 컨트롤을 바꿀 때마다 `× 1e-3` 왕복으로 저장됐습니다 → `LengthInputs`가 표시한 m 값을 기억해,
    손대지 않은 값은 비트 단위로 그대로(테스트). 상한이 꺼져 있을 때 보이는 10 mm도 켜는 순간 정확히 그 값이 들어갑니다.
  - 단위를 바꾸면 층 표·단면·최적화 패널을 새로 그림(단위가 바뀔 때만, 패널의 자체 편집을 방해하지 않게).
  - **기존 불일치(버그)**: 두께가 0인 층을 변수로 켜면 기본 범위가 속성 패널에서는 0.1–10 mm, 최적화 패널 "추가"에서는 0–1 m(1000 mm)였습니다.
    한 함수(`lengths.zero_thickness_range`)로 통일하고 단위에 맞췄습니다(mm 0.1–10 mm, µm 0.1–10 µm, nm 10–1000 nm).
  - 새 슬래브의 기본 두께 2 mm 고정 → 단위에 맞춤(mm 2 mm, µm 1 µm, nm 100 nm). nm 설계에 2 mm 층이 들어가면 단면에서 박막이 모두 최소 폭으로 찌그러졌습니다.
  - 변수 추가 목록의 단위 표시, 범위 입력의 저장 단위, 결과 표, 도움말의 단위 안내, 단위가 박힌 문구("Thickness {t} mm", "Total {t} mm") 교체.
- **캡처로 고친 것**: 최적화 목표 편집의 대역 행 라벨이 nm 값 옆에서 "주파수"로 남아 있었습니다(3.21에서 놓침). 해석 설정처럼 단위에 따라
  주파수·파장·파수로 바꾸고, 이름 함수를 `spectral.quantity_name`으로 모았습니다.
- **확인 예**: BK7 위 MgF₂(99.64 nm)·ZrO₂(134.1 nm) 2층 반사방지막을 nm로 보면 층 표·속성 칸·단면 총 두께(233.7 nm)·최적화 기준값(250 nm)·상한(400 nm)·
  변수 범위(50–200 nm 등)가 모두 nm로 보입니다(영문·한글 캡처). 속성 칸은 전에 `9.9640e-05 mm`였습니다.
- **검증**: 테스트가 229개에서 235개로 늘었고(변환·표시 단위 대응·저장·CLI·보고서 5개, GUI 1개), 맥 py3.10·3.13과 원격 Windows·WSL Linux × py3.10·3.13(커밋 `13da5b2`)의 여섯 환경에서 모두 통과합니다.

### 3.23 파장 등간격 스윕 격자 — 브랜치 `wavelength-grid`
3.21에서 미룬 항목입니다. 같은 흐름(코드 조사 → 계획 v1 → Argon 리뷰 → 확인 → 계획 v2 → 구현 → 캡처 → 원격 검증)으로 했습니다.
- **문제**: 스윕은 주파수 등간격이거나 로그였습니다. 파장 축으로 보면 주파수 등간격은 짧은 파장 쪽에 점이 몰립니다(400–800 nm에서 400 nm 쪽이 4배 촘촘).
  광학 스펙트럼은 보통 파장 등간격으로 계산하고 비교합니다. 로그 격자는 파장에서도 로그 등간격이라 그대로 둡니다.
- **설정**: `SweepSettings.uniform_wavelength`(bool). 해석 설정의 "점 간격" 콤보 상자(주파수 등간격 / 파장 등간격 / 로그)가 "로그 주파수 축" 확인란을 대신합니다.
  `log_f`는 그대로 두었습니다(Argon 동의 — 그래프·보고서·CLI·예제가 직접 읽음). 둘 다 켜진 상태(손으로 고친 파일·명세)는 로그로 정규화하고,
  풀이 캐시 키에는 실제 효과(`wavelength_spaced()`)를 넣어 같은 격자가 다른 키로 갈리지 않게 했습니다(Argon 지적).
- **격자** (`project.wavelength_grid`): 파장을 긴 쪽에서 짧은 쪽으로 등간격으로 만들어 주파수 오름차순으로 돌려줍니다(다른 코드가 모두 오름차순을 가정).
  양 끝은 정확히 f_min·f_max(c/(c/f) 왕복 오차 제거), n = 1이면 [f_min](linspace와 같게), 주파수가 0 이하면 `ValueError`. 기존 두 격자는 코드 경로를
  바꾸지 않아 비트 단위로 같습니다(테스트). 계획 v1의 "λ = linspace(c/f_max, c/f_min)"는 순서가 반대였는데 Argon이 짚었습니다.
- **따르는 곳**: `freq_grid`를 거치는 모든 곳 — 주파수·Smith·흡수 탭, 맵(`map_n_f`), 비교 곡선의 설계 스냅샷, 공차 분석 격자, 진단 격자, 보고서, Touchstone
  (비등간격 주파수도 형식상 허용), CLI `solve`. 재료 물성 탭과 재료 편집기 미리보기는 자기 격자를 만들던 것을 `freq_grid(n)`으로 바꿨고, 재료 편집기는
  격자 설정이 바뀌어도 다시 그립니다(Argon 지적). 측정 재료 미리보기와 피팅 대화상자는 데이터 범위를 쓰므로 그대로입니다.
- **따르지 않는 곳**: 최적화 목표 격자(`BandTarget.grid`)는 주파수 등간격 그대로입니다(Argon 동의). 목표마다 자체 `n_f`가 있고, 목표 마진·목적함수가
  스윕 설정에 흔들리지 않아야 하며, CLI 계약(`targets[].n_f`)에 영향을 주지 않습니다.
- **저장 형식 7** (내 판단, Argon은 이 질문에 답하지 않음): 표시 단위(3.21·3.22)와 달리 풀이하는 점이 바뀝니다. 이전 앱이 키를 무시하면 공차 수율 격자·
  그래프·내보내기·비교 곡선이 경고 없이 달라지므로 4장 원칙대로 올렸습니다. 옛 파일은 주파수 등간격으로 읽어 결과가 같습니다. 스키마 6을 고정해 둔
  테스트 세 곳(3.18·3.21·3.22)은 "현재 버전" 또는 "6 이상"으로 고쳤습니다.
- **CLI**: 명세 `sweep.uniform_wavelength`(참일 때만 내보냄, bool 아니면 `invalid_spec`), `info`의 `sweep`에 키 추가(CLI_PLAN 부록 B), `solve --linear-wavelength`.
  `--log-f`·`--linear-f`·`--linear-wavelength`는 상호 배타이고 각각 파일 설정을 대신합니다. 로그 파일에 `--linear-wavelength`를 줘도 로그가 우선하지 않도록
  셋을 한 값으로 묶었습니다(Argon 지적).
- **알려 둘 한계**: 파장 등간격은 고주파 쪽 간격이 (f_max/f_min)²배 넓습니다(2–18 GHz 301점이면 18 GHz 부근 간격이 선형의 약 9배). 좁은 고주파 대역이
  공차 격자 점 사이에 빠지면 기존 규칙대로 전체 스윕으로 판정합니다(3.20). 툴팁에 적었습니다.
- **확인**: 400–800 nm를 81점으로 잡으면 800, 795, …, 400 nm가 정확히 5 nm 간격으로 그려집니다(GUI 테스트). 해석 설정 캡처(영문·한글)로 콤보 상자 배치를 확인했습니다.
- **검증**: 테스트가 235개에서 241개로 늘었고(격자·저장·CLI 5개, GUI 1개), 맥 py3.10·3.13과 원격 Windows·WSL Linux × py3.10·3.13(커밋 `7a51ee5`)의 여섯 환경에서 모두 통과합니다.

### 3.24 보고서 PDF 직접 출력 — 브랜치 `report-pdf`
6장의 "보고서의 PDF 직접 출력"을 처리했습니다. 보고서는 HTML 한 파일이라 PDF가 필요하면 브라우저에서 인쇄해야 했습니다.
- **경과**: 코드 조사 → **시제품**(지금 HTML을 Qt로 그대로 PDF로) → 계획 v1 → Argon 리뷰 → 시제품 두 번 더 → 계획 v2 → 구현 → PDF를 그림으로 렌더해 확인 → 원격 검증.
- **방식** (Argon 동의): QTextDocument + QPdfWriter. PySide6의 필수 모듈(QtGui)만 쓰고 화면 없이 동기적으로 돕니다.
  QtWebEngine `printToPdf`는 CSS를 그대로 쓰지만 Chromium과 Linux·WSL 시스템 라이브러리·비동기 처리가 부담이고, matplotlib `PdfPages`는 표·문단을
  따로 배치해야 합니다. CLI에는 넣지 않았습니다(CLI는 Qt·matplotlib를 불러오지 않음, Argon 동의).
- **시제품이 보여 준 것**:
  - 지금 HTML을 그대로 `print_()`하면 제목·표·색·`data:` 이미지·쪽 번호는 되지만, 그래프가 쪽 폭을 넘어 오른쪽이 잘리고(CSS `max-width` 무시),
    표가 좁게 잡혀 머리글이 글자 단위로 줄바꿈되고("Polaris ation"), 110 dpi 그래프가 흐렸습니다.
  - 쪽 크기를 주지 않은 `print_()`는 문서화된 2 cm 여백을 더하고, 이미지·폭 단위가 플랫폼의 논리 DPI(오프스크린 96, macOS 보통 72)를 따릅니다. 고정 폭은
    어떤 플랫폼에서는 넘칩니다.
  - `<img width>`는 장치 DPI/기준 DPI만큼 배율이 붙고(300 dpi 장치에서 약 3.1배), 높이를 안 주면 원래 높이가 남아 그림 아래에 빈칸이 생깁니다.
  - SVG 그림은 그려지지만 `<img>` 크기로 래스터화됩니다(4배 확대에 계단, PDF에 이미지 객체). 그래서 200 dpi PNG를 씁니다(열린 질문 2).
- **설계**:
  - `report.build_report(print_layout=...)`(Qt 없음 유지): 200 dpi 그래프에 폭·높이를 지정하고, Qt가 읽는 CSS만 쓰며, 글자·테두리 색을 명시하고
    (다크 테마 팔레트가 흰 종이로 새지 않게 — 다크 팔레트로 실험해 확인), 넓은 표는 전체 폭, 층 표의 "#" 열은 4%. 브라우저용 HTML은 날짜와 이미지
    바이트를 빼면 이전과 같습니다(이전 코드와 비교해 확인). Qt 경계 테스트에 인쇄용 경로를 넣었습니다.
  - `gui/report_pdf.py`: 문서를 PDF 장치(300 dpi)에 배치하고 쪽 크기를 본문 영역으로 정해 쪽마다 직접 그립니다. 꼬리말은 "프로젝트 이름 … n / N".
    이미지 배율은 가정하지 않고 실행 중에 잽니다(폭 100 이미지를 배치해 실제 폭 측정). 글꼴은 matplotlib과 같은 후보 순서로 한글 가능 글꼴을 고릅니다.
  - **목록 다음 그림의 들여쓰기**: 공차 절에서 목록(`</ul>`) 바로 뒤 그림이 목록 들여쓰기를 이어받아 오른쪽이 잘렸습니다(렌더로 발견). 그림을 자기 문단에 넣었습니다.
  - 쓰기 전에 파이썬으로 파일을 열어 권한·잠김 문제를 그 시스템 메시지의 `OSError`로 냅니다. QPdfWriter는 실패를 알리지 않아, 덮어쓰기에 실패하면
    예전 PDF가 남아 성공처럼 보일 수 있었습니다(Argon 지적).
  - GUI: 파일 → "보고서 내보내기(PDF / HTML)". 저장 대화상자의 필터를 함께 받아 확장자 없는 이름은 고른 형식으로 정합니다. 예전 `_export_path`는 필터를
    버리고 `.html`을 강제해 "r.pdf"가 "r.pdf.html"이 될 수 있었습니다(Argon 지적). 툴팁의 "한 쪽짜리"도 바로잡았습니다.
- **한계** (Argon 지적, Qt에 쪽 넘김 avoid가 없음): 절 제목이 쪽 끝에 홀로 남을 수 있습니다. 강제 쪽 넘김은 넣지 않았습니다. 머리말은 없습니다(쪽 번호·이름 꼬리말로 충분, Argon 동의).
- **테스트에서 배운 것**: 처음 쓴 "오른쪽 여백에 잉크가 없는가" 검사는 그림을 30% 키워도 통과했습니다(넘친 부분은 잘려서 여백에 그려지지 않음). 레이아웃에서 각 그림의
  시작 위치와 폭을 재는 검사로 바꾸고, 그림 과대와 들여쓰기 두 버그를 일부러 넣었을 때 실패하는 것을 확인했습니다(5.4). 그 과정에서 `QTextLayout.lineAt`이
  아직 배치되지 않은 블록에서 프로세스를 죽인다는 것도 알았습니다(먼저 `blockBoundingRect`로 배치). QtPdf 렌더는 배경이 투명이라 픽셀 검사에서 주의가 필요합니다.
- **원격 실행에서 찾은 것 (Windows만 실패)**: 첫 원격 실행에서 Windows py3.10·3.13만 PDF 테스트가 실패했습니다. 쪽 수는 맞는데 추출한 글자가 빈 문자열이었습니다.
  SSH로 Windows에서 직접 확인하니, Qt의 offscreen 플랫폼(테스트·CI가 쓰는 것)은 Windows 글꼴 레지스트리를 읽지 않고 `PySide6/lib/fonts`를 찾는데 Qt가 더는
  글꼴을 싣지 않아 **글꼴을 하나도 찾지 못했고**, 그래서 글자 모양 없이 그려졌습니다. Linux(fontconfig)와 macOS는 문제없었고, 실제 Windows 앱은 `windows`
  플랫폼으로 시스템 글꼴을 써서 사용자에게는 영향이 없습니다. `QT_QPA_FONTDIR`을 `C:\Windows\Fonts`로 주자 Malgun Gothic이 선택되고 글자가 추출됐습니다.
  - `tests/conftest.py`가 Windows에서 offscreen이면 이 값을 정합니다(CI의 Windows 러너에도 적용).
  - Qt가 글꼴을 하나도 못 찾으면 `write_report_pdf`가 글자 없는 PDF를 조용히 쓰는 대신 `OSError`를 냅니다(테스트).
  - 원격 테스트가 없었다면 Windows에서만 깨진 채 머지됐을 것입니다(맥 py3.10·3.13은 통과).
- **확인**: Dual-band(공차 격자 결과 포함)를 영문(음수 RL)·한글(양수 RL) PDF로 만들어 세 쪽을 그림으로 렌더해 확인했습니다. 표가 전체 폭으로 펼쳐지고
  ("Polarisation"·"Rozanov bound" 한 줄), 그래프가 본문 폭에 맞고, 꼬리말 "1 / 3", 한글 글꼴이 정상입니다.
- **검증**: 테스트가 241개에서 243개로 늘었고(인쇄용 HTML 1개, PDF 쪽·글자·레이아웃·저장 형식 선택·쓰기 실패·글꼴 없음 GUI 1개), 맥 py3.10·3.13과 원격 Windows·WSL Linux × py3.10·3.13(커밋 `e7e43b2`)의 여섯 환경에서 모두 통과합니다.

### 3.25 Michielssen 1993 원문 대조 — 브랜치 `michielssen-original-tables`
- **계기**: HF1이 인쇄값 −23.5 dB보다 0.5 dB 좋게 계산되는 의문(3.16)이 남아 있었습니다. 사용자가 원문의 Table II·III과 Fig. 7을 화면에서 사진으로 찍어 줬습니다. Table I(재료표)과 본문은 보지 못했고, 사진은 저장소에 넣지 않습니다.
- **결론**: HF1의 재료·두께와 엔진 계산은 맞습니다. −23.5는 원문 Table II에 실제로 인쇄된 값이지만, 같은 논문의 Fig. 7 곡선과 맞지 않습니다. 왜 그 값이 인쇄됐는지는 알 수 없습니다.
  - Fig. 7을 사진에서 눈으로 읽은 값(오차 약 0.3 dB)과 계산: 대역 내 최댓값 약 6.3 GHz −24.0 dB(계산 6.33 GHz −24.02 dB), 최저점 약 7.75 GHz −27.1 dB(계산 7.75 GHz −27.19 dB), 0.1 GHz 약 −5.7 dB(계산 −5.77 dB).
  - HF1·HF2의 재료와 두께는 Goudos 재인쇄본과 정확히 같습니다.
- **원문에서 새로 알게 된 것**:
  - Table II와 III의 캡션이 서로 뒤바뀌어 인쇄됐습니다. LF 캡션 아래에 HF 표가 있습니다.
  - 원문의 1층은 PEC 쪽이고 5층이 입사면입니다. `reference.json`의 `layers`는 입사면부터이므로 표를 5층부터 거꾸로 옮겼습니다.
  - 인쇄된 HF 두께는 모두 0.003 mm, LF 두께는 모두 0.006 mm의 배수입니다.
  - 표의 최대 반사값은 정밀 비교 대상이 아닙니다. 계산과의 차이가 양쪽 방향으로 나고 1.5 dB까지 벌어집니다: HF1 −23.5/−24.02, HF2 −19.8/−19.68, HF3 −17/−18.48, HF4 −13/−12.87, LF1 −33/−32.5, LF2 −21/−20.57, LF3 −18/−18.0, LF4 −14/−15.5(인쇄/계산). LF4는 사진이 흐려 재료 번호를 잘못 읽었을 수 있습니다.
  - HF1의 "−16 at 40°"는 편광이 적혀 있지 않습니다. 계산은 TM −16.54 dB, TE −14.90 dB입니다. HF2는 Fig. 7의 점선이 겹쳐 읽지 못했습니다.
- **배제한 원인**: 주파수 격자(0.001–2 GHz 어느 격자도 HF1을 −23.5로 만들지 못하고, 성긴 격자는 최댓값을 낮춥니다), 재료 번호 한 개의 오식, 이완형 재료의 μ∞ = 1, 입사각·대역 차이(HF1과 HF2를 함께 설명하지 못함), 두께 숫자 한 자리의 오식(후보 세 개가 0.003 mm 격자 밖).
  - 재료 6의 지수를 0.596으로 적은 재인쇄본(*Ingeniería y Universidad* 18(1))이 있습니다. HF1은 −23.84 dB로 설명되지 않고, 재현되던 CFO·SADE 설계가 0.5 dB 넘게 어긋나므로 0.569를 유지합니다.
- **기록**: `reference.json`에 `original_tables`, HF3·HF4, `designs_lf`를 추가했고, 벤치마크 스크립트는 LF 설계를 보고만 합니다. 인쇄값이 느슨하므로 `must_reproduce`로 넣지 않았습니다. 데이터와 보고 출력만 바뀌어 앱 동작은 그대로입니다.

### 3.26 충전재 유효 파라미터 역산 (`invert-filler`, CLI_PLAN N9) — 브랜치 `filler-inversion`
- **경과**: 코드 조사 → 시제품 → 계획 v1 → Argon 리뷰(지적 14개) → 코드·실험으로 확인 → 계획 v2 → 설계 문서(CLI_PLAN 13.9) → 구현.
- **핵심 결정**: 결과는 충전재의 실제 물성이 아니라 혼합 모델에 묶인 유효값입니다. 시제품에서 1 % 잡음이 충전재 값에는 수십 %로 커져도, 같은 모델의 다른 함량 예측은 대개 0.2~2 %였기 때문입니다. 그래서 값의 신뢰도(κ)와 예측의 신뢰도(함량 ±10 %, 다른 혼합 모델, `--validate`)를 따로 보고합니다.
- **입력은 모두 필수**입니다. 모델, 매트릭스, 함량, 충전재 밀도에 기본값이 없습니다. 충전재 밀도를 1000으로 두면 `fraction_wt`와 질량 목적함수가 조용히 틀어집니다.
- **Argon 리뷰가 바꾼 것** (실험으로 확인):
  - Bruggeman 데이터를 MG로 처리하면 Re β > 1(1.66~2.50)인데도 수동성·왕복 검사를 통과합니다. 함량을 올리면 극점(1 − φβ = 0)에 다가가 예측이 커집니다(φ=0.3에서 최대 4.6배). 그래서 `outside_model` 판정을 넣었습니다.
  - 손실을 0으로 자른 표를 선형 보간하면, Re ε의 부호가 인접 점끼리 뒤집힌 경우 Fröhlich 극점을 지나 예측이 격자 사이에서 최대 45배 틀어집니다. 자르기는 Re > 0이고 모델 안인 점에만 허용합니다.
  - `load_csv`가 주석을 버려 GUI 가져오기에서 출처가 사라졌고, `fit`이 note를 덮어썼습니다. 둘 다 고쳤습니다.
  - 그 외: μ=1 채널의 거짓 악조건 경고(κ = 1/φ), `--force`로 입력 측정 파일을 덮어쓰는 위험, `material.csv` 상대 경로 문제, `_conductive`가 Re ε ≤ 0을 놓치던 기존 버그.
- **검증**: 합성 데이터뿐입니다. 저장소에 같은 재료계의 함량별 실측 세트가 없습니다(Duan은 분말, Kumar는 조성 변경, Laird는 함량 미상). 테스트는 243개에서 285개로 늘었습니다. 회귀 테스트 11개에 버그를 일부러 넣어 잡히는지 확인했습니다. 처음에는 기준 테스트가 실패한 채로 돌려 전부 "잡힘"으로 나왔고, 기준을 통과시켜 다시 돌리자 3개가 놓친 것으로 드러나 입력을 고쳤습니다.
- **미룬 것**: 6장에 적었습니다.

### 3.27 병렬 RLC 시트 — 브랜치 `parallel-rlc`
- **경과**: 코드 조사 → 계획 v1 → Argon 리뷰(지적 13개) → 코드로 확인 → 계획 수정 → 설계 문서 → 구현 → 영문·한글 캡처.
- **모델**: 1/Zs = 1/R + j(ωC − 1/(ωL)). 공진에서 Zs = R로 열리고 벗어나면 단락에 가까워져, 슬롯·개구형 패턴을 표현합니다. 직렬과 같은 수직 입사 집중 소자 값이고, 공차는 R·L·C를 따로 흔듭니다.
- **`L = 0`은 인덕터 없음**입니다. 직렬의 `L = 0`과 물리는 다르지만 "0이면 그 소자가 없다"는 사용 의미가 같고, 필드 형식과 파일 호환성을 유지합니다(Argon 동의).
- **Argon 리뷰가 바꾼 것**:
  - `L → 0⁺`은 단락, `L = 0`은 개방이라 불연속입니다. 범위가 0에 닿으면 `has_param`이 뒤집혀 최적화가 `KeyError`로 멈추므로, 병렬 `L`의 하한은 0보다 커야 합니다.
  - `resonance()`가 직렬만 처리해 f₀와 Q가 사라질 뻔했습니다.
  - `1/(1/R)`은 부동소수점에서 R로 돌아오지 않아(예: 49) `r / (1 + j r b)`로 계산합니다. 소자가 없을 때 상수 시트와 비트 단위로 같습니다.
  - 직렬에서 병렬로 바꿀 때 사용자가 비운 값을 기본값으로 덮어쓰지 않습니다. `info`의 `L_h`는 인덕터가 없으면 null입니다.
- **받지 않은 지적**: 소자가 없는 시트도 난수를 3번 소비한다는 지적은 직렬과 같은 동작이고 공차 동일성은 약속하지 않으므로 그대로 뒀습니다.
- **Rozanov 한계**: 코드를 바꾸지 않았습니다. 분로 인덕턴스는 저주파 등가 인덕턴스를 줄이기만 하므로 기존 판정은 그대로 필요조건입니다(유도에 의한 판단, 수치 검증은 하지 않음).
- **검증**: 해석 비교(공기 중 시트, 공진 Salisbury Γ = 0, 3 dB점, 에너지 균형)와 **같은 평면의 상수 시트 세 장과의 독립 대조**. 테스트는 285개에서 311개로 늘었습니다. 회귀 테스트에 버그 17개를 일부러 넣어 모두 잡히는지 확인했습니다(처음에 놓친 1개는 입력을 고쳤습니다).
- **캡처로 고친 것**: 영문 층 스택에서 "RLC∥ · f₀ 8.9 GHz"가 잘려 "RLC∥ f₀ 8.9 GHz"로 줄였습니다.
- **예제 프로젝트는 추가하지 않았습니다**. 단일 병렬 시트는 협대역 공진기가 되어 새로운 흡수체 유형을 보여 주지 못합니다(Argon 동의).

### 3.28 각도에 따라 변하는 FSS 시트 — 브랜치 `angle-dependent-fss`
- **경과**: 코드 조사 → 문헌 원문 확인 → 계획 v1 → Argon 리뷰(지적 13개) → 코드로 확인 → 계획 수정 → 설계 문서 → 구현 → 영문·한글 캡처.
- **근거**: Luukkonen et al., *IEEE TAP* **56**, 1624 (2008), arXiv:0705.3548의 페이지 이미지에서 식을 직접 읽었습니다. 금속 메시는 TM의 L(식 5), 패치 배열은 TE의 C(식 9)가 `1 − sin²θ/(2ε_eff)`로 변합니다. 기억과 달리 패치의 각도 의존은 TM이 아니라 TE였습니다.
- **모델**: RLC 시트의 L과 C에 편광별 계수를 둡니다. X_pol(θ) = X(1 + a·s²), s² = (k_x/k₀)² = n_inc² sin²θ. k_x는 층을 지나도 보존되므로 안쪽 시트에도 그대로 씁니다. 저장되는 것은 계수 네 개뿐이고, GUI의 프리셋(메시, 패치)은 계수에서 되짚습니다. 계수를 최적화 변수로 두지 않습니다. 물리적으로 만들 수 없는 값을 찾아낼 수 있기 때문입니다.
- **저장 형식 8**: 이전 앱이 `angle`을 무시하면 경고 없이 다른 결과가 나옵니다.
- **Argon 리뷰가 바꾼 것**: 없는 소자(`L = 0`, `C = None`)까지 양수 검사를 하면 정상 시트가 깨지므로 있는 소자만 검사합니다. 입사 매질이 분산이면 s²가 주파수마다 달라 `(k_x/k₀)²`로 계산합니다. `check`는 스윕 각도(대개 0°)만 풀어 문제를 놓쳤으므로 각도 격자도 시험합니다. Custom은 파일·명세에서 온 값일 때만 고를 수 있고, 상수 시트로 바꾸면 계수를 지웁니다. 잘못된 계수와 NaN을 거부합니다.
- **한계**: 해석식은 조밀 배열의 순수 메시·패치에 대한 것입니다. 병렬 RLC와 L·C가 함께 있는 패턴에 쓰는 것은 유추이며(Argon의 Babinet 논증은 '지식 기반'), 전파 해석으로 대조하지 않았습니다. 회절 로브가 생기면 유효하지 않지만 앱은 격자 주기를 모르므로 자동으로 검사하지 않습니다.
- **검증**: 공기 중 시트의 TE/TM 닫힌 식을 논문의 식 5·6·8·9와 직접 비교했습니다. 테스트는 311개에서 356개로 늘었습니다. 버그 23개를 일부러 넣어 모두 잡히는지 확인했습니다. 처음에 놓친 2개 중 하나는 테스트를 보강했고, 하나는 필요 없는 코드라 지웠습니다.

### 3.29 FSS 격자 치수에서 L·C 계산 (`fss-grid`) — 브랜치 `fss-grid-dimensions`
- **경과**: 코드 조사 → 계획 v1 → 리뷰 → 코드로 확인 → 계획 수정 → 설계 문서(CLI_PLAN 13.10) → 구현 → 영문·한글 캡처.
- **리뷰는 Argon이 아닙니다.** Argon 할당량이 초과돼(429) 사용자 결정으로 이 대화의 맥락이 없는 Claude 서브에이전트에게 같은 규칙으로 맡겼습니다. 다른 회사 모델의 교차 검증은 아닙니다. 지적 15개 중 인용은 모두 코드와 맞았고, 대부분 설계를 바꿨습니다.
- **식**: Luukkonen 2008의 식 4·5·6·8·9에서 메시 L = μ₀D/(2π)·ln(1/sin(πw/(2D))), 패치 C = (2ε₀ε_eff D/π)·ln(1/sin(πw/(2D))). 패치의 w는 패치 사이 **간격**입니다. 치수는 저장하지 않으므로 파일 형식은 그대로입니다.
- **리뷰가 바꾼 것**:
  - CLI 인자를 `--strip-width-mm`와 `--gap-mm`로 나눴습니다. 하나였을 때 패치 폭을 간격 자리에 넣으면 검사를 통과하고 C가 150배 틀립니다.
  - 기본 적용은 시트를 순수한 메시·패치로 만듭니다. 기본 시트의 남은 C가 메시의 리액턴스 부호를 뒤집습니다(10 GHz에서 +117 Ω → −202 Ω).
  - 유효 한계를 0.3·0.5 × c/(D√ε_eff) 두 단계로 뒀습니다. 처음 계획의 k_eff D = 2π는 회절 로브보다 높습니다. 0.5는 ε_eff = (ε_r+1)/2에서 어느 각도의 로브보다도 낮음이 증명되고, 0.3은 경험적 기준입니다(리뷰가 '지식 기반'으로 표시).
  - CLI 출력은 SI 키(`L_h`, `C_f`, `*_hz`)이고 명세용 단위는 `sheet` 조각에만 씁니다. 입력을 되돌려 주고 `assumptions`를 함께 냅니다.
  - 새 값이 L·C 변수 범위 밖이면 범위 재설정을 제안합니다. 그대로 두면 최적화기가 시작값을 범위 안으로 잘라 치수에서 얻은 값을 잃습니다.
- **한계**: 패치의 C는 ε_eff에 비례하지만 적용 뒤 패널에서 ε_eff를 바꿔도 C는 다시 계산되지 않습니다(툴팁에 적음). 정사각 격자, 이상 도체, 주축 평면 입사, w ≪ D를 가정합니다. R은 사용자 값이고 식에서 정해지지 않습니다. 스트립 배열은 패치와 프리셋을 구별할 수 없어 넣지 않았습니다. 전파 해석과 대조하지 않았습니다.
- **검증**: 식을 논문의 Zg와 여러 주파수에서 직접 비교했습니다. 테스트는 356개에서 416개로 늘었습니다. 버그 28개를 일부러 넣어 모두 잡히는지 확인했습니다. 놓친 1개는 키보드 추적을 켠 뒤 필요 없어진 코드라 지웠습니다.

## 5. 검증 원칙과 교훈

### 5.1 원칙
- **해석해는 독립적으로**: 비교용 닫힌 식은 솔버 코드를 보지 않고 테스트 안에서 직접 씁니다.
- **호환성 주장은 비트 단위로**: "예전과 같다"는 주장은 이전 알고리즘을 테스트 안에 동결해 두고 `==`로 확인합니다.
- **수치는 측정한 뒤에**: 예제 설명에 넣는 수치(성능 비교, 수율)는 직접 돌려서 얻은 값만 씁니다.
- **해석 테스트의 허용 오차는 늘리지 않습니다**(AGENTS.md).

### 5.2 교차 리뷰가 틀렸던 사례
리뷰 지적은 대부분 사실이었고 결과를 크게 개선했습니다. 다만 아래는 확인해 보니 틀렸습니다.

### 5.3 화면 캡처로만 찾은 문제
매 PR마다 테스트는 통과했지만 캡처에서 레이아웃 문제가 나왔습니다. 영문이 한글보다 길어서 주로 영문에서 생겼습니다.
- 그래프 도구 막대 넘침 (PR #5, #8)
- 속성 패널 가로 넘침 (PR #8)
- 층 스택 머리글 잘림 (PR #8)
- 결과 표 문구 잘림 (PR #7, 툴팁으로 해결)
- 실측 곡선이 각도를 따르지 않는다는 표시가 없음 (PR #6, "(측정)" 라벨)
- 한글 용어 충돌: "기준선"
- 층별 공차 표의 층 이름 잘림 (3.18, ρ 열 추가로 "1. …"가 됨. 왼쪽 패널을 40 px 넓힘)
- 공차 그래프 제목 끝 잘림 (3.19, 격자 모드 제목이 길어짐. 제목 줄바꿈)
- 캡처 스크립트가 `mplfonts.configure_matplotlib_fonts()`를 부르지 않으면 한글 그래프 글자가 빠집니다(앱 버그 아님, 캡처 전에 부를 것).

### 5.4 기타
- **측정 기록**: `solve`의 각도 축 벡터화 비용(Dual-band, 301 주파수): 각도 1개 0.47 ms, 7개 0.66 ms, 13개 1.07 ms(3.19 계획 단계).
  각도별로 따로 풀어도 공차 분석 전체가 수 초 안이라 정확성(비트 단위 같음)을 택했습니다.
- **결과는 실행 당시 설정을 들고 다닙니다**(3.20): 결과를 화면이나 보고서에 보여 줄 때 현재 설정을 다시 읽으면, 설정을 바꾼 뒤 결과와 설명이 어긋납니다. 결과를 만들 때 쓴 설정과 판정 구간을 결과에 함께 저장합니다.
- **테스트는 버그가 있을 때 실패하는지 확인합니다**(3.24): PDF의 "오른쪽 여백에 잉크가 없는가" 검사는 그림을 30% 크게 해도 통과했습니다. 넘친 부분은
  여백에 그려지지 않고 잘려 버리기 때문입니다. 레이아웃에서 이미지의 실제 위치를 재는 검사로 바꾸고, 일부러 버그를 넣은 두 경우(그림 과대, 목록 들여쓰기)에
  실패하는 것을 확인했습니다. 회귀 테스트는 고치기 전 상태로 한 번 돌려 봅니다.
- **리뷰 주장은 문서에 옮기기 전에 코드로 확인합니다**(3.22): 계획에 반영할 지적은 확인했지만, "미룬 작업"의 이유로 적은 리뷰 문장(두께 입력 최소 100 nm)은
  확인하지 않아 틀린 채 문서에 남았습니다. 문서에 쓰는 사실은 출처가 리뷰여도 `파일:줄`이나 실행으로 확인합니다.
- **원격 실행은 `&`로 띄우지 않습니다**(3.21): 원격 테스트를 셸의 `&`로 띄운 뒤 백그라운드 실행을 또 시작해, 두 실행이 Windows의 같은 폴더를
  동시에 썼습니다. 맥 쪽 두 실행을 멈추고 원격의 `win_test.ps1` 프로세스 트리만 골라 끝낸 뒤 하나만 다시 돌렸습니다. 원격 테스트는 도구의
  백그라운드 실행 한 개로만 돌리고, 겹침을 막는 잠금을 스크립트에 넣었습니다.
- **실례는 만들지 않습니다**: 기능의 효과를 보여 줄 사례를 찾지 못하면(3.19의 안쪽 각도가 더 나쁜 설계) 찾지 못했다고, 무엇을 봤는지와 함께 적습니다.
- 탭에 컨트롤을 추가할 때는 영문 1440–1500 px 폭에서 그래프 막대가 넘치지 않는지 확인합니다.
- 설정 변경(`doc.changed("settings")`)이 다른 패널 표시에 영향을 주면 `MainWindow._on_doc_changed`에서 해당 패널을 갱신합니다. 공차 대역과 속성 패널의 Zs(f_at)를 빠뜨린 적이 있습니다.

## 6. 미뤄 둔 작업
처리한 항목은 지웁니다. 다중 각도·다중 목표 몬테카를로 수율(#7)은 목표 꼭짓점 결합 수율(3.15)과 목표 각도 격자 수율(3.19)로 처리했습니다.
- 전용 다중 공진 시트 모델(#8)은 만들지 않고, 실제 수요가 생기면 재검토합니다(2026-11-09 결정). 병렬 가지 모델은 같은 평면 적층으로 표현할 수 있기 때문입니다.
  - 직렬 RLC 시트 두 장을 같은 평면에 쌓은 결과는 1/Zs = 1/Z1 + 1/Z2인 시트 한 장과 반사율 차이 최대 1.8×10⁻¹⁵로 같습니다(2–18 GHz, 0·30·60°, TE·TM, 엔진 계산).
  - 적층으로 얻지 못하는 것은 패턴당 GUI 객체 하나, 가지 사이의 공차 상관, 직렬 탱크 연결입니다. 가지 사이의 상호 결합은 전용 병렬 가지 모델로도 표현되지 않습니다.
  - GUI에서의 적층·편집·최적화와 각도 계수를 켠 적층은 시험하지 않았습니다. 사용 안내 문서화는 GUI 확인 후에 합니다.
  - Gemini(앱, 전체 배경을 준 질문)도 "만들지 말라"고 판정했습니다. 근거로 두 시트의 전달 행렬 곱이 어드미턴스 합이 된다는 점을 들었습니다. Zs(f, θ, 편파) 표 가져오기를 1순위 대안으로 꼽았지만 받아들이지 않았습니다. 표는 추출 때의 기판·간격·입사 조건에서만 유효하고 패턴 치수를 최적화할 수 없어, 전파 해석·측정 데이터가 있을 때만 의미가 있습니다.
  - **재검토 조건의 확인**: Gemini가 제안한 대로 이중 루프를 흉내 낸 합성 설계(RLC 시트 2장 + 스페이서, 6–18 GHz, 0–30°, TE+TM)를 `coating-cli`로 최적화하고 공차를 돌렸습니다. 값은 방법 확인용이며 실제 패턴이 아닙니다. 공칭 최악값은 −12.05 dB입니다. 적층 구성의 build·check·optimize·tolerance는 경고 없이 동작했습니다.
    - 시트 사이의 상관은 전용 모델의 근거가 되지 못합니다. 2,000개 표본, 각 인자 1σ = 5 %, 기준 −11 dB에서 시트 안의 L·C를 반대로 움직일 때 수율은 시트별 0.980, 두 시트 공통 0.962입니다. 같은 방향으로 움직일 때는 0.610과 0.678입니다. 차이는 5 %에서 최대 0.07이고, 10 %에서는 대부분 0.1 안쪽이지만 같은 방향·−11 dB에서 0.233과 0.395로 0.16까지 벌어졌습니다.
    - 큰 차이는 시트 **안**의 상관에서 나옵니다. R·L·C를 모두 독립으로 흔드는 현재 방식의 수율은 0.596(CLI와 일치)이고, L·C가 반대로 움직이면 0.980입니다(10 %에서는 0.138과 0.795). 이 한계는 공진이 하나인 시트에도 똑같이 있어, 다중 공진 모델로는 해결되지 않습니다. 실제 L·C 상관의 부호와 크기는 공정·패턴에 달려 있고 측정 자료가 없으므로, 여기의 상관은 가정입니다.
- 각도 계수와 격자 치수 식의 전파 해석 대조 (3.28, 3.29), 스트립 배열(3.29)
- 재료 모델 파라미터(f₀·γ)의 광학 단위 입력 (3.21에서 제외. 파장 등간격 격자는 3.23에서 처리)
- `invert-filler`의 GUI 대화상자, 여러 함량 CSV의 동시 역산, 비구형 형상 인자 (3.26)
