# Coating Studio 성능 검증 시나리오 (v2)

앱(GUI)과 CLI가 "정확한가, 빠른가, 최적화가 잘 되는가, 결과가 재현되는가"를 한 번에 확인합니다.
**합격 기준은 측정 전에 고정**하고, 측정 후에 기준을 고쳐 합격시키지 않습니다.
측정 스크립트: `examples/validation/performance_check.py WORKDIR`.

## 환경과 측정 규칙

- macOS, Apple M1 Max(10코어), 64 GB, conda `coat-py313`. 커밋 해시와 버전을 결과에 함께 적습니다.
- GUI는 `QT_QPA_PLATFORM=offscreen`으로 실제 `MainWindow`를 구동합니다.
- T3의 시간은 벽시계 기준이며, 워밍업 1회를 버리고 7회 반복의 중앙값과 사분위수 범위(IQR)를 적습니다.
- 최적화 설정은 앱 기본값입니다(`maxiter 150`, `popsize 15`, 다듬기 켬). T4는 프로세스 4개를 동시에 돌립니다.
- 기준의 10% 안쪽으로 붙은 합격은 "간신히 합격"으로 표시합니다.

## 판정

- **필수** 항목이 하나라도 실패하면 전체 불합격입니다. 나머지는 항목별로 보고하고 실패 원인을 적습니다.

## 리뷰 반영 (Gemini)

- **반영**: T2를 배열 일치로 강화, T3a 기준 강화, T3의 워밍업·7회 반복, T4a의 시드 10개·중앙값 기준, T5b의 표본 배열 비교, T5c의 구간 명시, T6c를 `tracemalloc`으로 교체, T4d·T6d·T6e·T8 추가.
- **반영하지 않음**: T3c ≤ 30 ms. 디바운스가 연속 편집 중 재계산을 막으므로 프레임 예산을 적용할 근거가 약하고, 해당 위험은 T6e로 직접 측정합니다.
- **한정해서 유지**: T6a. offscreen은 렌더링을 재현하지 않지만, 작업 스레드의 GIL 경합은 측정됩니다.

### 불합격과 측정 한계의 원인

- **T6a는 실제 문제였고 고쳤습니다.** 최적화가 약 7초 도는 동안 메인 스레드가 1.6 s와 5.1 s 멈췄습니다. 멈춘 동안의 스택은 matplotlib의 `constrained_layout` 그리기였고, 작업 스레드는 `solve`를 돌고 있었습니다. GIL 전환 주기를 바꿔 재니 최대 멈춤이 5 ms에서 5,958 ms, 1 ms에서 6,711 ms, 200 µs에서 296 ms, 50 µs에서 91 ms였습니다. `start_worker`가 주기를 50 µs로 줄이도록 고쳤습니다. 최적화 시간은 7.1 s에서 10.2 s로 늘었고, 밀려 있던 그래프 그리기가 실제로 실행되기 때문으로 보입니다. 실제 화면에서는 재지 않았습니다.
- **T6c는 측정 방식의 문제로 보이지만, 기준상 불합격으로 둡니다.** `tracemalloc`을 워밍업 뒤에 켜서, 살아 있는 결과 배열과 그래프 객체가 처음 교체될 때 증가분으로 잡혔습니다. 진단 실행에서 90회 간격 증가량은 2556, 2565, 2569, 2575, 2578, 2581 KB로, 처음 90회 이후 450회 동안 25 KB만 늘었습니다. 다음 판에서는 추적을 켠 뒤 워밍업을 해야 합니다.
- **수정 전 T6b의 최적화 값(0.000 s)은 의미가 없습니다.** 측정 창 8초 안에 최적화가 먼저 끝나 정지 요청이 실행 중 작업에 닿지 않았습니다. 수정 후에는 최적화가 8초 넘게 돌아 0.048 s가 실제 지연입니다.

## 알려진 한계

- 절대 시간은 이 맥에서만 유효합니다. GUI의 실제 화면 렌더링은 측정하지 않습니다.
- 전파 해석이나 측정과의 대조는 범위 밖입니다.
